## 병렬로 바꿀 때 확인할 점

[OrderKafkaProducer.java:24](src/main/java/com/whale/order/domain/order/service/OrderKafkaProducer.java#L24) 가 키를 `orderId` 로 넣고 있습니다:

```java
kafkaTemplate.send(TOPIC, String.valueOf(orderId), orderId).get();
```

키가 `orderId` 라 같은 주문은 항상 같은 파티션에 가고, **한 주문의 이벤트 순서는 병렬화해도 보장**됩니다. 서로 다른 주문끼리는 순서가 섞여도 무관하니 `concurrency: 3` 을 켜도 정합성 문제는 없습니다. 재고 차감은 [Redisson 분산 락](src/main/java/com/whale/order/domain/stock/repository/StockRepository.java#L13)이 따로 직렬화하므로 이쪽도 안전합니다.

다만 **운영에서는 켜도 의미가 없습니다.** [application-prod.yaml:39](src/main/resources/application-prod.yaml#L39) 가 `kafka.enabled: false` 라 프로덕션은 Kafka 자체를 안 쓰고 [OrderEventListener](src/main/java/com/whale/order/domain/order/service/OrderEventListener.java) 의 동기 폴백으로 돕니다. 즉 지금 Kafka 경로는 로컬 dev 전용이고, 컨슈머 1개로도 부하가 없어서 문제가 드러나지 않은 상태입니다.

**면접 대비로는** 이 상태를 그대로 말하는 게 낫습니다 — "파티션 3개로 확장 여지를 뒀지만 concurrency는 기본값 1이고, 파티션 키를 orderId로 잡아둬서 늘려도 주문 단위 순서는 깨지지 않는 구조"까지 말하면 설계를 이해하고 있다는 게 전달됩니다. 주석만 보고 "3개 병렬로 처리합니다"라고 답하면 `concurrency` 어디 있냐는 질문에 막힙니다.

Spring Kafka 리스너 설정값입니다. **"이 리스너를 컨슈머 스레드 몇 개로 돌릴까"** 를 정하는 숫자입니다.

`@KafkaListener` 를 붙이면 Spring이 뒤에서 `ConcurrentMessageListenerContainer` 를 만드는데, 이 컨테이너가 `concurrency` 값만큼 **내부 컨슈머를 생성**합니다. 각 내부 컨슈머는 자기만의 `KafkaConsumer` 인스턴스와 스레드를 갖고, 같은 그룹(`whale-order`)의 멤버로 브로커에 등록됩니다. 그러면 브로커가 리밸런싱해서 파티션을 나눠줍니다.

```java
// 현재 — concurrency 없음 → 기본값 1
@KafkaListener(topics = "order-created", groupId = "whale-order")

// 스레드 3개
@KafkaListener(topics = "order-created", groupId = "whale-order", concurrency = "3")
```

또는 전역으로:
```yaml
spring:
  kafka:
    listener:
      concurrency: 3
```

## 왜 필요한가

[OrderKafkaConsumer.consume()](src/main/java/com/whale/order/domain/order/service/OrderKafkaConsumer.java#L25) 이 `orderProcessingService.process(orderId)` 를 호출합니다. 이게 DB 쓰고 재고 락 잡고 하느라 예를 들어 100ms 걸린다고 하면:

```
concurrency = 1  →  초당 10건 (한 건 끝나야 다음 건)
concurrency = 3  →  초당 30건 (세 건 동시에)
```

메시지가 쌓이는 속도가 처리 속도보다 빠르면 컨슈머 랙(lag)이 계속 늘어납니다. 그때 **서버를 늘리지 않고 프로세스 안에서 병렬도를 올리는 손잡이**가 이겁니다.

## 상한이 파티션 개수인 이유

Kafka는 **한 파티션을 그룹 내 컨슈머 하나에게만** 배정합니다. 순서 보장을 위한 규칙입니다. 그래서:

| concurrency | 파티션 3개일 때 |
|---|---|
| 1 | 스레드 1개가 파티션 3개 담당 ← 현재 |
| 3 | 스레드 3개, 각 1개씩 — 최적 |
| 5 | 3개만 일하고 **2개는 영구 유휴** |

[KafkaConfig.java:23](src/main/java/com/whale/order/global/config/KafkaConfig.java#L23) 의 `.partitions(3)` 이 병렬도 상한을 3으로 정해둔 것이고, `concurrency` 가 그 안에서 실제로 몇 개를 쓸지 고르는 값입니다. 파티션이 천장, concurrency가 현재 높이입니다.

## 헷갈리기 쉬운 지점

`concurrency` 를 늘려도 **파티션 하나 안에서는 여전히 순차**입니다. 스레드 3개가 같은 파티션을 나눠 처리하는 게 아니라, 파티션별로 담당자가 갈릴 뿐입니다. 그래서 [OrderKafkaProducer.java:24](src/main/java/com/whale/order/domain/order/service/OrderKafkaProducer.java#L24) 가 키를 `orderId` 로 넣은 게 중요합니다 — 같은 주문은 항상 같은 파티션 → 같은 스레드 → 순서 보장. 병렬화해도 한 주문의 이벤트가 뒤바뀌지 않는 이유입니다.

키를 `null` 로 뒀다면 라운드로빈으로 흩어져서 같은 주문의 이벤트 두 개가 다른 스레드에서 동시에 처리될 수 있습니다. 그게 "파티션 키 설계"가 Kafka에서 중요한 이유고, 면접에서 자주 파고드는 지점입니다.

## 1단계: CI에서 JUnit 자동 실행 (가장 가치 큼)

[deploy.yml:8](.github/workflows/deploy.yml#L8) 위에 job을 하나 추가하고 기존 job이 그걸 기다리게 합니다:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: gradle
      - name: 테스트 실행
        run: ./gradlew test
      - name: 테스트 결과 업로드
        if: always()          # 실패해도 리포트는 남긴다
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: build/reports/tests/test/

  build-and-push:
    needs: test               # ← 테스트 통과해야 빌드 진행
    runs-on: ubuntu-latest
    ...
```

`needs: test` 한 줄이 **배포 게이트**입니다. 테스트가 깨지면 이미지가 만들어지지도 않습니다.

Testcontainers가 걸림돌일까 걱정할 수 있는데, `ubuntu-latest` 러너에는 Docker가 이미 있어서 [TestContainerBase](src/test/java/com/whale/order/support/) 의 PostgreSQL·Redis 컨테이너가 그대로 뜹니다. `@EmbeddedKafka` 도 인메모리라 문제 없습니다. 다만 컨테이너 시작 때문에 3~5분 걸릴 수 있습니다.

## 2단계: k6를 "자동화 가능한 형태"로 바꾸기

여기가 핵심입니다. k6 스크립트를 CI에 넣기 전에 **판정을 기계가 읽을 수 있게** 만들어야 합니다.

[order-load-test.js:35](k6/order-load-test.js#L35) 는 이미 되어 있습니다:
```js
thresholds: {
  http_req_duration: ['p(95)<2000'],
  payment_fail_rate: ['rate<0.05'],
}
```
`thresholds` 를 위반하면 k6가 **exit code 99** 로 죽습니다. CI가 이걸 실패로 인식합니다.

반면 [stock-concurrency-test.js](k6/stock-concurrency-test.js) 는 `thresholds` 가 없습니다. [teardown](k6/stock-concurrency-test.js#L169-L182) 이 `💥 오버셀 발생` 을 `console.log` 로 찍고 끝나서, **오버셀이 나도 k6는 exit 0** 입니다. 사람이 로그를 눈으로 봐야 아는 구조라 자동화가 불가능합니다.

고치는 방법은 판정 결과를 메트릭으로 올리는 것입니다:

```js
import { Counter } from 'k6/metrics';
const oversell = new Counter('oversell_detected');

export const options = {
  scenarios: { ... },
  thresholds: {
    oversell_detected: ['count==0'],   // 하나라도 감지되면 테스트 실패
  },
};

export function teardown(data) {
  // ... 기존 재고 조회 로직
  if (remaining < 0 || deducted > initial) {
    oversell.add(1);                   // ← console.log 대신(또는 함께) 카운터
    console.log(`💥 오버셀 발생`);
  }
}
```

이러면 `docker run ... ; echo $?` 가 0이 아닌 값을 내고, CI가 빨간불을 켭니다.

## 이 테스트가 실제로 잡아주는 것

세 번째 케이스가 핵심입니다. [OrderCursorPagingTest.java:122](src/test/java/com/whale/order/domain/order/service/OrderCursorPagingTest.java#L122) 가 `created_at` 을 전부 같은 값으로 UPDATE 해버립니다:

```java
jdbcTemplate.update("UPDATE orders SET created_at = TIMESTAMP '2026-07-27 14:03:22.481'");
```

`created_at` 단일 커서였다면 동률 구간이 통째로 누락되거나 무한 루프에 빠집니다. 복합 커서 `(created_at, order_id)` 를 쓴 이유를 정면으로 증명하는 케이스라, **면접에서 "커서 페이징 왜 썼냐"에 이 테스트를 근거로 답할 수 있습니다.**

## 관련해서 짚어둘 만한 지점

1. **Redis 는 폴백이 없다** — Kafka 는 `kafka.enabled=false` 로 동기 폴백이 있는데(`application-prod.yaml`), Redis 는 그런 스위치가 없습니다. 결제·장바구니·분산락·세션 전부 Redis 의존이라 Redis 다운 = 사실상 서비스 중단.

2. **커넥션 타임아웃이 응답 지연을 만든다** — Redisson 기본 `connectTimeout` 이 10초라, Redis 가 죽었는데 클라가 요청을 계속 보내면 톰캣 스레드(`max-threads: 50`)가 10초씩 잡혀 앞단이 먼저 마비될 수 있습니다. 프로덕션이라면 `timeout`, `retryAttempts` 를 짧게 (예: 1초/1회) 튜닝하는 게 좋습니다.

3. **"Redis 죽으면 어떡할 거냐" 는 포트폴리오 질문 단골** — 두 갈래로 답할 수 있습니다:
   - **Fail fast (현재 방식)** — 결제 중복 방어를 못하는 상태에서 진행하는 게 더 위험. 죽으면 5xx 로 명확히 실패시키고 클라가 재시도.
   - **Degraded mode** — 멱등검사만 DB `UNIQUE(idem_key)` 백업으로 폴백. 코드 복잡도 vs. 가용성 트레이드오프.
