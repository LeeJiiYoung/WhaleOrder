```

프론트:     POST /api/auth/exchange { code }    ← 본문으로 교환

**A. `@SQLRestriction` 제거 + 필요한 곳에만 명시적 필터** ← 추천

`Member` 엔티티에서 `@SQLRestriction` 을 떼고, 탈퇴 회원을 진짜로 막아야 하는 곳에만 조건을 겁니다. 대상은 4곳뿐입니다.

| 위치 | 변경 |
|---|---|
| [MemberRepository.java:17](src/main/java/com/whale/order/domain/member/repository/MemberRepository.java#L17) `findByUserId` | → `findByUserIdAndIsDeletedFalse` (로그인) |
| [MemberRepository.java:20](src/main/java/com/whale/order/domain/member/repository/MemberRepository.java#L20) `findByProviderAndProviderId` | → `...AndIsDeletedFalse` (카카오 로그인) |

| [MemberRepository.java:26-42](src/main/java/com/whale/order/domain/member/repository/MemberRepository.java#L26-L42) 어드민 목록/OWNER 검색 | → JPQL에 `AND m.isDeleted = false` |

메서드명에 조건이 박히니 빠뜨리면 컴파일이 안 되고, 그 외 `findById`(주문 생성·결제 등)는 그대로 동작합니다. 주문 이력에서 `getMember()` 는 정상적으로 익명화된 회원을 돌려줍니다.

**B. `@SQLRestriction` 유지 + `Orders.member` 에 `@NotFound(IGNORE)`**

건드리는 파일은 적지만 `@NotFound` 는 Hibernate에서 **LAZY를 무시하고 즉시 로딩을 강제**합니다. 매장 주문 목록마다 회원 조회가 N+1로 붙습니다. TPS/Latency 측정이 프로젝트의 핵심인데 거기에 조회를 심는 건 방향이 안 맞습니다. 그리고 `member` 가 `null` 이 되어 `OrderResponse` 외에 `Orders.member` 를 쓰는 모든 곳에 null 체크가 번집니다.

**C. 그냥 두고 탈퇴 회원 주문은 목록에서 제외**

가장 쉽지만 사장님 입장에서 **매출 집계가 조용히 틀어집니다.** 팔린 주문이 화면에서 사라지는 건 버그를 데이터로 감추는 쪽에 가깝습니다.

## 1. API

```
DELETE /api/members/me
Authorization: Bearer {accessToken}
Body: { "password": "..." }   // LOCAL 필수, KAKAO 생략

|---|---|---|
| OWNER / ADMIN | 403 | [SecurityConfig.java:70](src/main/java/com/whale/order/global/config/SecurityConfig.java#L70) 에 `.requestMatchers(DELETE, "/api/members/me").hasRole("CUSTOMER")` — 기존 URL 규칙 패턴 그대로 |

## 2. 익명화 규칙 — `Member.withdraw()`

| 컬럼 | 값 | 이유 |
|---|---|---|
| `userId` | `deleted_{memberId}` | unique 충돌 회피 → 같은 아이디 재가입 가능 |
| `providerId` | `deleted_{memberId}` (KAKAO만) | `uq_member_provider` 회피 → 카카오 재가입 가능 |
| `name` | `탈퇴한 회원` | 주문 목록 표시용 |
| `nickname` | `null` | — |
| `phone`, `password` | `null` | 개인정보 파기 |
| `isDeleted` | `true` | — |

`nickname` 을 null로 두면 [OrderResponse.java:23](src/main/java/com/whale/order/domain/order/dto/OrderResponse.java#L23) 의 기존 fallback이 `name` 을 집어서 `탈퇴한 회원` 을 출력합니다. **`OrderResponse` 는 손댈 필요가 없습니다.**

## 3. 서비스 흐름 — `MemberService.withdraw()`

```
1. findById(memberId)
2. role != CUSTOMER  → 403 (SecurityConfig 이중 방어)
3. provider == LOCAL → passwordEncoder.matches() 검증
4. 진행 중 주문(PENDING·PREPARING) 존재 → 409
5. member.withdraw()                    ← DB 트랜잭션
6. refreshTokenService.delete(memberId) ← Redis
7. cartService.clearCart(memberId)      ← Redis
```

6·7은 트랜잭션 롤백 대상이 아니지만 문제되지 않습니다. 리프레시 토큰이 남아도 4번의 인증 차단(아래)에 걸리고, 장바구니는 TTL 24시간으로 자동 소멸합니다.
