## 섹션 2/7 — 데이터 모델

```sql
CREATE TABLE kafka_outbox (
    id            BIGSERIAL PRIMARY KEY,
    topic         VARCHAR(100) NOT NULL,
    aggregate_id  VARCHAR(64)  NOT NULL,   -- orderId. Kafka 파티션 키로 사용
    payload       JSONB        NOT NULL,   -- {"orderId": 123}
    status        VARCHAR(20)  NOT NULL,   -- PENDING / PUBLISHED / FAILED
    attempts      INT          NOT NULL DEFAULT 0,
    last_error    TEXT,
    created_at    TIMESTAMP    NOT NULL DEFAULT NOW(),
    published_at  TIMESTAMP
);

-- 워커 폴링 최적화: PENDING인 것만 인덱스에 존재 (partial index)
CREATE INDEX idx_kafka_outbox_pending
    ON kafka_outbox (created_at)
    WHERE status = 'PENDING';

-- 청소 배치 최적화: 오래된 PUBLISHED 조회
CREATE INDEX idx_kafka_outbox_published_at
    ON kafka_outbox (published_at)
    WHERE status = 'PUBLISHED';
```

**설계 이유 요약**

| 컬럼 | 이유 |
|-----|-----|
| `topic` | 나중에 다른 이벤트(예: `payment-cancelled`)도 붙일 수 있게 범용성 |
| `aggregate_id` | Kafka `send(topic, key, value)` 의 key로 사용 → 같은 order는 같은 파티션 |
| `payload` JSONB | 문자열보다 검색·디버깅 편함. 이 프로젝트가 PostgreSQL이라 자연스러움 |
| `attempts` | 최대 5회 판단용 |
| `last_error` | FAILED 원인 사후 확인용 |
| `published_at` NULL 허용 | PENDING/FAILED 상태에선 아직 발행 안 됨 |

**Partial Index 두 개**
- PENDING partial index: 폴링 쿼리가 항상 최신 순 스캔이라, PENDING만 인덱스에 담아두면 처리 끝난 row는 자동으로 인덱스에서 빠짐. **폴링 부하 최소화의 핵심**.
- PUBLISHED partial index: 매일 청소 배치 (`WHERE status='PUBLISHED' AND published_at < NOW() - 7 days`) 최적화.

**엔티티 매핑 (JPA)**
- `KafkaOutbox` 엔티티에 `enqueue()`/`markPublished()`/`markFailedOrRetry(Exception)` 상태 전이 메서드를 두어 상태 변경을 엔티티가 캡슐화. 워커/서비스는 원시 setter 안 씀.
- Payload는 `@Type(JsonBinaryType.class)` (Hibernate 6) 또는 `String`으로 두고 JSON 직렬화는 서비스에서. **이 프로젝트가 어느 걸 쓰는지에 맞춰** 결정 — 기존 JSONB 사용처가 있으면 그대로 따름, 없으면 String으로 단순화.

**시나리오: `outboxService.enqueue()`가 실패한다면**

```java
// pay() 트랜잭션 안
try (트랜잭션) {
    INSERT payment
    INSERT order
    kafkaOutboxService.enqueue("order-created", orderId, payload)  ← ★ 여기 실패
    eventPublisher.publishEvent(...)
    COMMIT
}
```

`enqueue()`는 그냥 `INSERT kafka_outbox` 한 줄이라 실패 원인은 DB 이슈 뿐:
- 커넥션 끊김
- DB 다운
- 디스크 풀
- 테이블 락 타임아웃

**어떻게 되냐면 — 전체가 통째로 롤백됩니다.**

- `KafkaOutboxService`는 `@Transactional`로 호출자 트랜잭션에 참여(REQUIRED). 예외를 던지면 `pay()` 트랜잭션이 rollback-only로 마킹됨.
- `payment` INSERT, `order` INSERT까지 다 취소.
- 사용자에겐 결제 실패 응답. 카드도 청구 안 됨(Mock PG 기준).

**이게 왜 좋냐면 — "결제는 됐는데 이벤트가 없다"가 원천 불가능해집니다.**

| Before (AFTER_COMMIT 리스너) | After (Outbox in-tx) |
|--|--|
| pay() 커밋 ✓ → Kafka publish ✗ → **유령 주문** | outbox INSERT ✗ → pay() 전체 롤백 → **결제 자체가 없던 일** |

즉 outbox 저장 실패는 "이벤트 유실" 문제가 아니라 **"결제 실패"** 로 변환됩니다. 사용자한텐 명확한 에러가 가고, DB엔 아무것도 안 남고, 재시도할 여지 명확.

**설계상 지켜야 할 것 (놓치면 원자성 깨짐)**

1. `KafkaOutboxService.enqueue()` 안에서 **예외를 catch로 삼키면 안 됨.** 그대로 던져야 pay()가 롤백됨.
2. `pay()` 안에서도 `enqueue()` 호출을 try-catch로 감싸면 안 됨. 감싸는 순간 "이벤트는 없는데 결제만 성공" 시나리오 부활.
3. `KafkaOutboxService`에 `@Transactional(propagation = REQUIRED)` (기본값) — 새 트랜잭션 만들면 안 됨. `REQUIRES_NEW`는 절대 금지.

이 3가지를 스펙 문서에 명시적 경고로 넣겠습니다. 코드 리뷰 시 실수하기 쉬운 지점.

- 여전히 원자적.

1. **트랜잭션 두 개**

   - 두 트랜잭션 사이에 시간 갭(최대 1초) 존재. 이게 outbox의 "지연" 대가.

2. **워커 트랜잭션을 row별로 여는 이유**

3. **dev/prod 분기 지점**

   - dev: `kafkaTemplate.send(topic, aggregateId, payload).get()` — `.get()` 으로 발행 확인까지 동기 대기.
   - prod: `orderProcessingService.process(orderId)` 직접 호출.
   - 둘 다 성공 시 `markPublished()`.

4. **cart clear의 위치**
   - Redis 작업이라 outbox 대상 아님. AFTER_COMMIT 리스너 유지.
   - cart clear 실패해도 사용자 결제엔 영향 없음 (기존 정책 유지).

| 1 | `outbox INSERT` 실패 (DB 이슈) | `pay()` 전체 롤백 | 사용자 재시도. 결제/주문/outbox 모두 없음. **완벽한 원자성** |
| 2 | `pay()` 커밋 직후 JVM 크래시 | outbox row = PENDING 상태로 DB에 남음 | 재시작 후 워커가 자동으로 발행. **유령 주문 없음** |
| 3 | Kafka 브로커 다운 | 워커 발행 실패 → attempts++ | 브로커 복구 후 다음 폴링에서 자동 재시도 |
| 4 | 워커 발행 성공, `UPDATE PUBLISHED` 실패 (DB 순단) | Kafka엔 발행됨, DB엔 PENDING 유지 | 다음 폴링에서 재발행 → **Consumer 중복 수신** → `isStockDeducted` 방어로 흡수 |
| 5 | `send().get()` 타임아웃 | attempts++, PENDING 유지 | 다음 폴링에서 재시도 |
| 6 | 5회 재시도 후에도 실패 | status=FAILED, attempts=5 | 폴링 대상에서 제외. `kafka_outbox_failed_total` 카운터 증가. **수동 개입** |
| 7 | prod 모드에서 `process()` 실행 중 예외 | attempts++, PENDING 유지 | 다음 폴링에서 재시도 (Consumer 재시도와 동일 층위) |
| 8 | 워커 자체 스레드 죽음 (Spring 스케줄러 이슈) | 폴링 자체 중단 | `kafka_outbox_pending_count` gauge가 계속 증가 → Grafana 알림. **모니터링으로 감지** |
| 9 | 청소 배치 실패 | 오래된 PUBLISHED row 안 지워짐 | 다음 날 새벽 3시에 재시도. 며칠 밀려도 디스크 여유 있으면 무해 |

**핵심 코드 스니펫**

```java
// KafkaOutboxWorker
@Scheduled(fixedDelay = 1000)
public void publishPending() {
    List<KafkaOutbox> pending = outboxRepository
        .findTop100ByStatusOrderByCreatedAtAsc(PENDING);

    for (KafkaOutbox row : pending) {
        // row별 개별 트랜잭션 — 실패 격리
        try {
            processOne(row);
        } catch (Exception e) {
            // 여기까지 오면 트랜잭션도 롤백, attempts도 반영 안 됨
            // → 다음 폴링에서 다시 잡힘 (같은 상태로)
            log.error("[Outbox] 워커 처리 실패 outboxId={}", row.getId(), e);
        }
    }
}

@Transactional
protected void processOne(KafkaOutbox row) {
    try {
        publish(row);              // dev: Kafka.send / prod: process()
        row.markPublished();        // status=PUBLISHED, published_at=NOW()
    } catch (Exception e) {
        row.markFailedOrRetry(e, 5);  // attempts++, 5회 초과 시 FAILED
        // 트랜잭션 커밋됨 → attempts 반영
    }
}
```

**주의점 하나**: `processOne`의 `catch`가 예외를 삼키고 있음. 이건 의도적 — 발행 실패는 outbox 상태(attempts++)에 기록만 하고 다음 폴링을 기다리게 만들기 위해서. `catch` 없으면 매번 예외 로그 폭발 + 트랜잭션 롤백으로 attempts 업데이트도 안 됨.

**FAILED 알림 정책**
- 로그 error + `kafka_outbox_failed_total` 카운터.
- Slack/이메일 연동은 이 프로젝트 스코프 밖.
- 기존 Grafana 대시보드에 패널 하나 추가 예정 (섹션 7).

**시나리오 4번 재조명 — 왜 Consumer 중복 방어가 필수인가**

Outbox는 근본적으로 **at-least-once** 보장. "정확히 1번 발행"은 불가능(발행-업데이트 사이 크래시 = 재발행). Kafka 자체도 at-least-once. 그래서 Consumer 멱등성이 outbox 도입의 **전제 조건**인데, 이 프로젝트는 이미 `OrderProcessingService.processOrder()`에 `if (order.isStockDeducted()...) return;` 방어가 있어서 조건이 이미 충족됨.

**Grafana 대시보드 패널 추가 (기존 대시보드에 얹기)**
```
┌──────────────────────────────────┬────────────────────────────┐
│ Outbox Pending (gauge, 실시간)   │ Outbox Published Rate (rpm)│
├──────────────────────────────────┼────────────────────────────┤
│ Outbox Failed (누적)             │ Outbox Publish Latency*    │
└──────────────────────────────────┴────────────────────────────┘
```
`*Publish Latency` = `published_at - created_at`. 정상 시 평균 500ms 근방. 급등하면 워커가 밀린 것.
