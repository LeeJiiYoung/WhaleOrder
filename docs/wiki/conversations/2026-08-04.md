## 지금 운영 환경에서는 못 돌립니다

[docker-compose.prod.yml:1-12](docker-compose.prod.yml#L1-L12) 에 적혀 있듯 운영은 **t3.micro(RAM 1GB)** 이고 **Kafka를 아예 안 씁니다**(`kafka.enabled=false`, 동기 폴백). 브로커 하나가 기본 힙 1GB를 잡으므로 **3브로커면 최소 3~4GB**가 필요합니다.

그래서 현실적인 선택지는 셋입니다.

| | 비용 | 용도 |
|---|---|---|
| **로컬 3브로커** | 0원 (내 PC RAM 4GB) | 학습·시연·장애 실험 ← **추천** |
| EC2 t3.medium 이상 | 월 3~4만원 | 실제 운영 |
| AWS MSK / Confluent Cloud | 월 10만원~ | 실무 방식 |

포트폴리오 목적이면 **로컬 3브로커로 장애 주입 실험까지 하고 문서로 남기는 게** 가장 효율이 좋습니다. 아래는 그 기준입니다.

## 1. 현재 구조 — HA가 아닌 이유

[docker-compose.yml:36-54](docker-compose.yml#L36-L54)

```yaml
KAFKA_NODE_ID: 1
KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093   # 컨트롤러도 1대
KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1      # 오프셋도 복제 안 됨
```

[KafkaConfig.java:24,34](src/main/java/com/whale/order/global/config/KafkaConfig.java#L24)

```java
.replicas(1)   // order-created, order-created.DLT 둘 다
```

**브로커 하나가 죽으면 전부 정지**입니다. 데이터도, 컨슈머 오프셋도, DLT도 복구 불가입니다. wiki [한계 섹션](docs/wiki/architecture/kafka-event-stream.md)에도 "DLT Consumer가 단일 노드 → replica 늘리기 필요"로 이미 적혀 있습니다.

## 2. HA는 "무엇을 견딜 것인가"를 먼저 정하는 일

숫자 세 개가 전부입니다.

| 설정 | 값 | 의미 |
|---|---|---|
| `replication.factor` | 3 | 파티션 사본 3개 |
| `min.insync.replicas` | 2 | 쓰기 성공에 필요한 최소 동기 사본 |
| `acks` | all | ISR 전원 확인 후 ack |

**RF=3 + minISR=2 조합의 결과**

- 브로커 1대 다운 → **쓰기·읽기 정상** (사본 2개 남음)
- 브로커 2대 다운 → **쓰기 실패**, 읽기만 가능 (의도된 동작 — 유실보다 거부가 낫다)

`min.insync.replicas=1` 로 두면 1대만 남아도 쓰기가 되지만, 그 1대가 죽으면 **데이터가 사라집니다.** HA를 한다면서 이 값을 1로 두는 게 가장 흔한 실수입니다.

## 3. 로컬 3브로커 구성

KRaft 조합 모드(broker+controller)로 3대를 띄웁니다. `CLUSTER_ID` 는 **세 대가 같아야** 합니다.

```yaml
  kafka1:
    image: confluentinc/cp-kafka:7.6.0
    container_name: whale-kafka1
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      # 3대 모두 동일하게 나열 — 컨트롤러 쿼럼(과반 2/3)
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka1:9093,2@kafka2:9093,3@kafka3:9093
      KAFKA_LISTENERS: PLAINTEXT://kafka1:9092,PLAINTEXT_HOST://0.0.0.0:29092,CONTROLLER://kafka1:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka1:9092,PLAINTEXT_HOST://localhost:29092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: PLAINTEXT:PLAINTEXT,PLAINTEXT_HOST:PLAINTEXT,CONTROLLER:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT
      # ── HA 핵심 ──
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 3          # 컨슈머 오프셋도 복제
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 3
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 2
      KAFKA_DEFAULT_REPLICATION_FACTOR: 3
      KAFKA_MIN_INSYNC_REPLICAS: 2
      KAFKA_UNCLEAN_LEADER_ELECTION_ENABLE: "false"      # 뒤처진 사본을 리더로 승격 금지 = 유실 방지
      CLUSTER_ID: MkU3OEVBNTcwNTJENDM2Qk
    ports: ["29092:29092"]
    networks: [whale-net]
```

`kafka2`·`kafka3` 는 `NODE_ID`, 호스트명, 포트(`29093`, `29094`)만 바꿔 복제합니다.

**`KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 3` 을 빠뜨리면 무의미합니다.** 토픽은 복제되는데 `__consumer_offsets` 가 1이면 그 브로커가 죽는 순간 **컨슈머가 어디까지 읽었는지 잃어버립니다.**

접속 주소도 3개 모두 적습니다 — 하나가 죽어도 부트스트랩이 됩니다.

```yaml
KAFKA_BOOTSTRAP_SERVERS: localhost:29092,localhost:29093,localhost:29094
```

## 4. 앱 설정 변경

**토픽 복제본을 환경별로** — [KafkaConfig.java](src/main/java/com/whale/order/global/config/KafkaConfig.java) 의 `.replicas(1)` 하드코딩을 프로퍼티로 뺍니다.

```java
@Value("${kafka.topic.replicas:1}")          private int replicas;
@Value("${kafka.topic.min-insync-replicas:1}") private String minIsr;

@Bean
public NewTopic orderCreatedTopic() {
    return TopicBuilder.name("order-created")
            .partitions(3)
            .replicas(replicas)
            .config(TopicConfig.MIN_IN_SYNC_REPLICAS_CONFIG, minIsr)
            .build();
}
```

**DLT에도 똑같이 적용해야 합니다.** 지금 `partitions(1).replicas(1)` 인데, DLT가 죽으면 **실패한 주문의 보상 처리가 통째로 날아갑니다.** 정상 경로보다 오히려 더 중요합니다.

**프로듀서 보장 명시** — 현재 [application.yaml:32-34](src/main/resources/application.yaml#L32-L34) 에 `acks` 가 없습니다. Kafka 3.x 클라이언트 기본값이 `acks=all` + 멱등성이라 지금도 안전하지만, **HA 설정은 기본값에 기대면 안 됩니다.** 명시하세요.

```yaml
    producer:
      acks: all
      retries: 2147483647
      properties:
        enable.idempotence: true
        delivery.timeout.ms: 120000
```

## 5. 함정 — 기존 토픽은 RF가 안 늘어납니다

**`NewTopic` 빈은 없는 토픽을 만들 뿐, 이미 있는 토픽의 복제본을 바꾸지 않습니다.** 설정만 3으로 올리고 재시작하면 `order-created` 는 조용히 RF=1로 남습니다.

기존 볼륨을 지우고 새로 만들거나(로컬이면 이게 편합니다), 재배치를 돌려야 합니다.

```bash
docker compose down -v && docker compose up -d      # 로컬: 그냥 초기화
# 운영: kafka-reassign-partitions.sh 로 온라인 재배치
```

## 6. 검증 — 브로커를 실제로 죽여봐야 합니다

설정만 넣고 "HA 구성함"이라고 하면 의미가 없습니다.

```bash
# 1) ISR 3개 확인
docker exec whale-kafka1 kafka-topics --bootstrap-server kafka1:9092 \
  --describe --topic order-created     # Isr: 1,2,3

# 2) 리더 브로커를 죽인다
docker stop whale-kafka2

# 3) 그 상태로 주문을 넣어 성공하는지 확인 (k6 부하 테스트 재사용)
# 4) ISR 축소 확인 — Isr: 1,3 이지만 minISR=2 충족이라 쓰기 정상
# 5) 하나 더 죽이면? → 쓰기 실패해야 정상
docker stop whale-kafka3
```

**5번에서 실패하는 걸 확인하는 게 핵심입니다.** 실패해야 `min.insync.replicas=2` 가 실제로 걸려 있다는 증거입니다.

## 7. 남는 단일 장애점

브로커 3대를 **한 도커 호스트**에 띄우면 그 PC가 죽을 때 전부 죽습니다. 실제 HA는 가용영역을 나눠야 합니다. 그리고 이 프로젝트는 **애플리케이션 자체가 1대**라, Kafka만 HA로 만들어도 앱이 죽으면 서비스는 멈춥니다.

시연·학습 목적이라면 이 한계를 문서에 명시해두는 편이 낫습니다 — 면접에서 "이건 진짜 HA는 아니고 브로커 레벨만"이라고 먼저 말하는 쪽이 훨씬 좋게 평가됩니다.

정확히 나누면 **"무슨 장애를 막고 싶으냐"에 따라 다릅니다.**

| 장애 유형 | 한 서버에 3브로커 | 여러 서버에 3브로커 |
|---|---|---|
| 브로커 프로세스 죽음 (OOM·크래시·재시작) | **막힘** | 막힘 |
| 디스크 하나 깨짐 | **막힘** | 막힘 |
| 호스트 다운·네트워크 단절 | 못 막음 | 막힘 |
| 가용영역(AZ) 장애 | 못 막음 | AZ 분리 시 막힘 |

**한 서버에 3개를 띄워도 무의미하지 않습니다.** 실무에서 가장 흔한 Kafka 장애는 호스트가 통째로 날아가는 게 아니라 **브로커 프로세스가 죽거나 재시작되는 것**입니다 — 롤링 업그레이드, OOM, 디스크 풀. 그건 한 호스트에서도 진짜로 방어됩니다.

다만 "고가용성 달성했다"고 말하려면 여러 서버가 맞습니다. 한 호스트는 그 호스트가 SPOF니까요.

## 그런데 이 프로젝트에선 순서가 다릅니다

[docker-compose.prod.yml](docker-compose.prod.yml) 을 보면 운영 구성이 이렇습니다.

```
backend    1대   ← 죽으면 서비스 전체 정지
postgres   1대   ← 죽으면 주문·결제·회원 전부 정지
redis      1대   ← 죽으면 장바구니·분산락·세션 정지
kafka      0대   ← 아예 안 씀 (kafka.enabled=false)
```

**Kafka만 3중화하는 건 균형이 안 맞습니다.** 안 쓰는 컴포넌트를 HA로 만들면서, 죽으면 전부 멈추는 DB는 1대로 두는 셈이니까요.

가용성이 진짜 목적이라면 우선순위는 이 순서입니다.

1. **PostgreSQL** — 죽으면 아무것도 안 됨. RDS Multi-AZ가 가장 효과 큼
2. **애플리케이션 2대 + 로드밸런서** — 무중단 배포도 같이 얻음
3. **Redis** — 분산 락이 걸려 있어 죽으면 재고 차감이 멈춤
4. Kafka — 지금은 꺼져 있어서 죽어도 영향 없음

## 그래서 추천은

**목적이 "가용성 확보"라면** Kafka HA는 지금 할 일이 아닙니다. 위 1~3번이 먼저입니다.

**목적이 "복제·ISR·페일오버를 이해하고 보여주는 것"이라면** 로컬 한 대에 3브로커로 충분합니다. 여러 서버로 늘려도 **배우는 내용은 똑같습니다** — RF, `min.insync.replicas`, 리더 선출, 컨슈머 리밸런싱 전부 한 호스트에서 그대로 관찰됩니다. 서버를 늘려서 추가로 얻는 건 호스트 장애 내성 하나뿐이고, 그건 돈으로 사는 것이지 설계로 얻는 게 아닙니다.

면접 관점에서도 **"브로커 레벨 장애는 막지만 호스트는 SPOF다"** 라고 스스로 한계를 짚는 쪽이, 여러 서버에 띄워놓고 이유를 설명 못 하는 것보다 낫습니다.

어느 쪽으로 가실지 정해주시면 그에 맞춰 진행하겠습니다.
