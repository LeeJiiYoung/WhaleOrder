## 왜 같은 트랜잭션이면 안 되는가

낙관적 락 충돌은 **커밋 시점**에 발생합니다. 예외가 나온 순간 트랜잭션은 이미 `rollback-only` 로 마킹돼 있어서, 그 안에서 뭘 해도 커밋되지 않아요. `stockService.deductStock()` 을 다시 호출해봤자 같은 트랜잭션이면 무조건 롤백입니다.

그래서 재시도는 **반드시 새 트랜잭션**이어야 합니다 — 새로 Stock 을 읽어서 최신 `version` 을 확보하고, 그 상태에서 다시 UPDATE 를 시도해야 성공할 여지가 생깁니다.

## Spring 이 실제로 새 트랜잭션을 시작하는지 확인 포인트

- `StockLockFacade.deductStock()` 에는 `@Transactional` 이 없음 → 바깥 트랜잭션 없음
- 호출자인 `OrderProcessingService.processOrder()` 도 `@Transactional` 없음
- `StockService.deductStock()` 은 `@Transactional(timeout=10)` — 기본 propagation `REQUIRED`
- 바깥에 트랜잭션이 없으므로 매 호출마다 **새 트랜잭션이 열림**

## 다만 한 가지 유지되는 것 — Redisson 락

트랜잭션은 매번 새로 열리지만, **Redisson 분산 락은 재시도 사이에도 계속 잡고 있습니다** (`tryLock` 은 재시도 루프 바깥, `finally unlock` 도 바깥). 그래서:

- 다른 스레드가 이 (storeId, menuId) 로 끼어들지 못함
- 재시도 사이에 새로 읽는 Stock 값은 안정적
- 대부분 2회차에서 즉시 성공 (충돌 원인이 다른 트랜잭션의 커밋이었다면, 그 커밋은 이미 끝났고 새 version 을 읽으면 그만)

즉 **"락은 유지, 트랜잭션은 갱신"** 이 낙관적 락 재시도의 정석 패턴이고, 지금 구현이 그 형태입니다.

## 진짜 REST-정합적 답 — `202 Accepted`

HTTP 스펙 자체가 이런 케이스를 위해 `202 Accepted` 를 정의해뒀습니다:

> "The request has been accepted for processing, but the processing has not been completed."

async 처리에서 표준적으로 쓰는 코드입니다. 완료 상태를 알려면 별도 채널(폴링용 endpoint 또는 SSE) 을 통해 조회하라는 게 REST 규약. 이 프로젝트에는 이미 SSE 가 그 역할을 하고 있으니 딱 들어맞습니다.

즉 지금 구조를 **REST 원칙에 완전히 정합적으로** 만들려면:

```java
// PaymentController.pay()
return ResponseEntity
        .accepted()                                     // 202
        .header("Location", "/api/orders/" + response.orderId())  // 상태 조회 URL
        .body(ApiResponse.ok("결제가 완료되었습니다. 주문 처리 진행 중입니다.", response));
```

응답 body 문구도 "결제 완료 + 주문 처리 중" 으로 조정해서, 사용자/클라이언트가 "이 시점에 완결된 게 결제뿐이고 주문은 진행 중" 이라는 걸 알게 하면 됩니다.

3. **후반**: HTTP 스펙에서 정확한 답(`202 Accepted`) 을 짚고, 그걸 자기 프로젝트에 어떻게 적용할지까지 (`Location` 헤더 + 기존 SSE 연계) — **HTTP 스펙 정독 + 실전 적용 능력**을 동시에 보여줌

## 추가 방어 카드 — RESTful 원칙 vs 실용성

혹시 더 파고들면:

> "REST 는 원칙이지 종교가 아닙니다. ## 솔직히 말씀드리면 — 실무에서 잘 안 씁니다

REST 스펙상으로는 202 가 맞지만, 실제 프로덕션 API 는 대부분 **200 + body 로 상태 표현** 방식을 씁니다. 앞서 드린 "202 가 정답" 답변은 **면접 방어용으로는 강력하지만, 실무 현실과는 갭이 있습니다.** 정직하게 알고 계셔야 할 부분이라 정리해 드립니다.

## 어디서 202 를 실제로 쓰는가

**쓰는 곳** (스펙 준수형 API):
- AWS SDK (S3 배치 작업, Lambda async invoke)
- Kubernetes API (long-running operations)
- Azure / GCP 일부 async 엔드포인트
- 대형 파일 처리·비디오 인코딩 API (Mux, Cloudflare Stream 등)
- 공개 개발자 API 로 문서화가 중요한 서비스들

**안 쓰는 곳** (대다수):
- 국내 이커머스·핀테크 (토스, 카카오페이, 배민, 쿠팡 등 — 정확한 내부는 모르지만 일반적으로 200 관행)
- 대부분 B2C REST API
- Stripe 조차도 대부분 200 (async 케이스에서도)
- 사내용 마이크로서비스 대다수

## 왜 실무는 200 을 고집하는가

1. **프런트 라이브러리가 2xx 를 구분 안 함** — axios, fetch 는 200/202 둘 다 `response.ok = true` 로 뭉뚱그림. 클라이언트 코드에서 202 분기 태우려면 매번 `response.status === 202` 명시적 처리 필요
2. **상태는 body 로 관리하는 관행** — `{status: "PROCESSING"}` / `{status: "COMPLETED"}` 필드로 표현. HTTP 상태 코드 대신 도메인 상태 필드로 통일
3. **모니터링·로그 도구 편향** — Grafana·Datadog·Sentry 는 대체로 2xx 를 한 버킷으로 묶음. 202 만 따로 알람 걸려면 별도 설정 필요
4. **팀 지식 편차** — 백엔드 개발자 중 202 를 정확히 아는 사람 생각보다 적음. 코드 리뷰 때 "왜 200 안 쓰고 이상한 거 씀?" 리뷰 나옴
5. **클라이언트 계약 복잡화** — 202 를 도입하는 순간 프런트와 "202 오면 상태 조회 별도로 해라" 는 약속이 필요. 안 지켜지면 오히려 UX 깨짐

## 그럼 이 프로젝트는 실무 관점에서 어떻게 가야 하나

**실무형 절충안** — 200 유지하되 응답 body 를 명확히:

```java
return ResponseEntity.ok(ApiResponse.ok(
    "결제가 완료됐습니다. 주문 처리 중입니다.",  // ← 문구 조정: "완료" 가 아니라 "처리 중"
    response  // response 에 이미 status 필드 있음 (payment.status = SUCCESS)
));
```

여기에 응답 스펙에 **"주문 최종 상태는 SSE `/api/orders/sse` 채널에서 통지된다"** 를 명시하면, 200 유지하면서도 클라이언트가 착각할 여지가 줄어듭니다. **실제로 상태 코드 바꾸는 것보다 계약(문구+SSE 존재) 을 명확히 하는 게 실무에서 더 중요합니다.**

## 면접에서는 어떻게 답할지

면접관이 "202 로 바꾸겠냐" 라고 물으면, 이제는 이렇게 답할 수 있습니다:

> "스펙적으로는 202 가 정답이지만, 실무에서는 대다수 서비스가 200 + body status 필드 방식을 씁니다. 프런트가 2xx 를 구분 안 하는 관행, 모니터링 도구가 2xx 를 뭉뚱그리는 편향, 팀 지식 편차 등이 이유입니다.
>
> 그래서 이 프로젝트라면 **HTTP 코드는 200 유지**, 대신 **응답 message 를 '결제가 완료됐습니다' → '결제가 완료됐습니다. 주문 처리 중입니다' 로 바꾸고**, API 문서(Swagger) 에 **'최종 주문 상태는 SSE 채널로 통지된다'** 를 명시하는 방향으로 갈 것 같습니다. 상태 코드보다 계약을 명확히 하는 게 실제 오해를 줄이는 데 효과적이라는 판단입니다.
>
> 물론 공개 API 나 개발자용 SDK 를 만든다면 202 를 정직하게 쓰는 게 맞습니다. 프로덕트 성격에 따라 다를 것 같습니다."

## 정리 — 실무 감각의 척도

| 답변 유형 | 어떤 인상 |
|-----------|-----------|
| "202 로 바꾸겠습니다" | 스펙은 아는데 실무 경험 얕음 |
| "200 이 관행이라 그대로 갑니다" | 원칙 모름 / 편함 추구 |
| **"스펙은 202, 실무는 200. 이 프로젝트는 [이유] 로 [선택]"** | 원칙-실무 갭 인지, 상황별 판단 가능 |

세 번째가 시니어 답변입니다. 면접관이 "202 로 바꾸겠냐" 를 물은 진짜 이유는 대개 **원칙과 실무 갭을 얼마나 감각하는지**를 보려는 겁니다. "스펙대로 다 바꾸겠다" 는 오히려 감점 요소일 수 있습니다.

## 앞선 제 답변 정정

이전 답변에서 "202 를 우선순위로 처리할 부분" 이라고 드렸는데, 이건 **면접 방어에는 강한 답이지만 실무 판단으로는 조금 과했습니다**. 실서비스로 이관한다면 코드 상태 바꾸는 것보다:

1. 응답 message 문구 조정 (완료 → 처리 중)
2. Swagger/API 문서에 SSE 연계 명시
3. 프런트와 "결제 200 = 접수 완료, 최종 상태는 SSE" 계약 확정

이 세 가지가 훨씬 우선순위 높습니다. 상태 코드는 마지막 미세 조정.
