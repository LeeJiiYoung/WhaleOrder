## 지금 대시보드의 p50/p95/p99 패널은 데이터가 안 나옵니다

## 히스토그램 활성화 범위

`percentiles-histogram` 은 Timer 하나당 수십 개의 `_bucket` 시계열을 만듭니다. `http.server.requests` 는 URI × status × method 조합마다 곱해지므로 시계열이 급증합니다.

- **선택지 A (추천) — 지표별 선별 활성**: `http.server.requests`, `order.processing.time`, `stock.lock.wait` 세 개만 켜고, `service-level-objectives` 로 버킷 경계를 직접 지정(예: 50ms/100ms/500ms/1s/2s/5s)해 버킷 수를 10개 내외로 묶습니다. 시계열 증가폭이 통제되고, 시연에서 보여줄 세 그래프는 전부 살아납니다.
- **선택지 B — 전역 활성(`all: true`)**: 설정 한 줄로 끝나지만 기본 버킷이 촘촘해서 Timer 하나당 60~70 시리즈가 붙습니다. [docker-compose.monitoring.yml:10](docker-compose.monitoring.yml#L10)에 t3.micro 메모리가 빠듯하다고 적혀 있는 상황이라 위험합니다.
- **선택지 C — 히스토그램 대신 `percentiles`**: 앱이 직접 p95를 계산해 값으로 내보냅니다. 설정은 쉽지만 **인스턴스/URI 간 합산이 수학적으로 불가능**해서 `sum by (uri)` 같은 집계가 깨집니다. 2026-07-27 대화록에도 같은 이유로 정리돼 있습니다.

**A를 추천합니다.** 시연 대상 세 지표만 정확히 살리면서 메모리 비용을 최소화합니다.
