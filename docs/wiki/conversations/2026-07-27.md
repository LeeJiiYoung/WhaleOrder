## SHA-256을 고른 이유 3가지

| 이유 | 설명 |
|------|------|
| **고정 길이 압축** | 장바구니에 아이템이 1개든 50개든 raw 문자열 길이가 제각각. 해시하면 항상 64자 hex로 고정 → Redis 키로 안전하게 사용 (길이/특수문자/개행 문제 제거) |
| **결정성(deterministic)** | 같은 장바구니·결제정보 → 항상 같은 해시 → 같은 멱등 키. "따닥" 중복 결제 요청이 동일 키로 매핑되어 1회만 처리 |
| **충돌 저항성** | 내용이 조금이라도 다르면(수량 1개 차이 등) 완전히 다른 키. 서로 다른 주문이 우연히 같은 키가 되어 "이미 처리됨"으로 잘못 막히는 사고를 사실상 배제 |

## 짚어둘 점 — 여기서 SHA-256은 "보안용"이 아님

이 해시는 서명·인증이 아니라 **콘텐츠 지문(fingerprint)** 용도입니다. 따라서 엄밀히는 암호학적 강도가 필수는 아니고, 기능적으로는 비암호 해시(예: MurmurHash)로도 충분합니다. 그럼에도 SHA-256을 쓴 건 합리적인데:

- **JDK 내장** — 별도 의존성 없이 `MessageDigest`로 바로 사용
- **MD5/SHA-1 대비 안전한 기본값** — 이 둘은 충돌이 실증돼 "깨진" 알고리즘. 굳이 그걸 쓸 이유가 없음
- 성능도 이 규모(요청당 1회)에선 전혀 병목이 아님

5번이 특히 중요합니다. 이벤트 대기열은 "선착순 정렬 + 내 순번 즉시 조회"가 요구사항인데, ZSet은 그게 자료구조의 기본 연산입니다. Kafka에는 "내가 몇 번째냐"를 물어볼 방법이 없습니다.

## Kafka 도입 기준 — 아래가 **모두** 성립할 때

| # | 기준 | 이 프로젝트 사례 |
|---|------|-----------------|
| 1 | **응답을 기다릴 필요 없는 후처리** | 결제 성공 응답은 이미 나갔고, 재고 차감·SSE 푸시는 그 뒤 ([overview.md ⑧~⑩](docs/wiki/architecture/overview.md)) |
| 2 | **실패해도 유실 불가 + 자동 재시도·보상 필요** | `FixedBackOff(1s×3)` → DLT → `compensate()` ([KafkaConfig.java](src/main/java/com/whale/order/global/config/KafkaConfig.java), [OrderKafkaConsumer.java:38-49](src/main/java/com/whale/order/domain/order/service/OrderKafkaConsumer.java#L38-L49)) |
| 3 | **순간 폭증을 버퍼링해야 함** | 파티션 3 + orderId 키 해싱 → 병렬 처리하되 같은 주문은 순서 보장 |

2번이 Kafka를 쓰는 **진짜 이유**입니다. 1·3번만 필요하면 Redis 큐나 `@Async`로도 됩니다. "실패한 메시지가 어디로 가는가"에 답이 필요할 때 비로소 Kafka입니다.

## 실제 판단 사례 — 주문 대기열은 왜 Redis에서 Kafka로 넘어갔나

코드에 그대로 남아 있습니다:

- [OrderQueueWorker.java:5](src/main/java/com/whale/order/domain/order/service/OrderQueueWorker.java#L5) — `// Kafka 도입 후 비활성화 — OrderKafkaConsumer가 대체` (빈 클래스 껍데기)
- [OrderQueueService.java:25](src/main/java/com/whale/order/domain/order/service/OrderQueueService.java#L25) — `// Kafka 기반으로 전환되어 Redis ZSet은 사용 안 함 → DB PENDING 카운트로 대체`
- `enqueue()`는 현재 **아무 데서도 호출되지 않음** (컨트롤러가 `getPosition()`만 호출)

반면 **이벤트 대기열(`event:queue:{eventId}`)은 여전히 Redis**입니다. 같은 "대기열"인데 갈린 이유가 기준 그 자체입니다:

| | 주문 대기열 → Kafka | 이벤트 대기열 → Redis 유지 |
|---|---|---|
| 목적 | 처리를 **흘려보냄** | 순번을 **보여줌** |
| 실패 시 | 재시도·DLT·보상 필수 | 다음 스케줄러 턴에 다시 처리하면 됨 |
| 유실 위험 | ZSet `popMin` 직후 프로세스 죽으면 주문 증발 | 대기 중 유실은 재입장으로 복구 가능 |
| 조회 요구 | 없음 | `rank()`로 내 순번 즉시 조회 |

정리하면 — **"꺼낸 뒤 죽으면 곤란한가?"** 가 Redis 큐와 Kafka를 가르는 선입니다. Redis ZSet은 `popMin` 하는 순간 메시지가 사라지고 재시도 장치가 없지만, Kafka는 커밋 전까지 offset이 남아 재처리·DLT가 성립합니다.

## 그런데 HTTP 응답이 나가는 시점은 다릅니다

두 모드가 갈리는 지점은 [OrderEventListener.java:42-45](src/main/java/com/whale/order/domain/order/event/OrderEventListener.java#L42-L45) 딱 한 줄입니다:

```java
orderKafkaProducer.ifPresentOrElse(
        p -> p.publish(event.orderId()),              // kafka.enabled=true
        () -> orderProcessingService.process(...)     // kafka.enabled=false → 동기 호출
);
```

`@TransactionalEventListener(AFTER_COMMIT)`는 **커밋한 그 스레드에서 동기 실행**됩니다. 그래서:

| | HTTP 응답이 나가기까지 |
|---|---|
| **Kafka OFF** | 결제 + **재고 차감 + 분산 락 대기 + SSE 푸시** 전부 끝난 뒤 |
| **Kafka ON** | 결제 + publish ack (수 ms) |

응답에서 빠지는 건 "재고 차감 연산 시간"이 아니라 **락 대기 시간**입니다. [StockLockFacade.java:33](src/main/java/com/whale/order/domain/stock/service/StockLockFacade.java#L33):

```java
if (!lock.tryLock(5, TimeUnit.SECONDS))
```

`stock:lock:{storeId}:{menuId}` — 같은 매장 같은 메뉴 주문은 **한 줄로 직렬화**됩니다. 평상시엔 몇 ms지만, 인기 메뉴에 몰리면 뒤에 선 사람은 최대 5초를 기다립니다. Kafka OFF면 그 5초 동안 톰캣 스레드가 물려 있습니다.

## 그래서 진짜 이득은 응답 속도가 아닙니다

**1. 스레드 격리 — 이게 제일 큽니다**

운영은 [application-prod.yaml:48-50](src/main/resources/application-prod.yaml#L48-L50)에서 톰캣 스레드가 **50개**입니다. Kafka OFF 상태에서 인기 메뉴 하나에 50명이 몰리면 50개 스레드가 전부 같은 락 앞에 줄 섭니다 → **메뉴 조회·로그인·매장 검색까지 전부 정지**합니다. 주문 안 한 사람들이 같이 죽는 겁니다.

Kafka를 끼면 락 경합이 컨슈머(파티션 3)로 격리됩니다. 주문 처리만 느려지고 나머지 API는 삽니다. **응답 시간을 지키는 게 아니라 응답 가능성을 지키는 것**입니다.

**2. 실패 처리 장치가 동기 모드엔 아예 없습니다**

Kafka OFF에서 재고 차감이 실패하면 `publishOrderEvent`의 catch가 잡아서 로그+메트릭만 남기고 끝입니다 ([OrderEventListener.java:47-53](src/main/java/com/whale/order/domain/order/event/OrderEventListener.java#L47-L53)). 주석대로 *"주문은 PENDING 상태로 남으므로 수동 재처리 필요"*. Kafka ON이면 3회 재시도 → DLT → `compensate()` 자동 보상입니다.

## SSE 부분 — 여기가 오해의 핵심 같습니다

"SSE는 어차피 카프카 끝나고 간다"는 맞습니다. 그런데 **동기 모드로 바꿔도 SSE는 여전히 필요합니다.**

이유: `process()`가 AFTER_COMMIT에서 도니까 **이미 결제는 커밋된 뒤**입니다. 재고 차감이 실패해도 롤백되지 않고, `OrderEventListener`가 예외를 잡아버려서 **사용자는 어차피 HTTP 200을 받습니다.** 즉 동기로 만들어도 재고 결과를 HTTP 응답에 담을 수 없습니다.

두 신호의 의미가 처음부터 다릅니다:

| | 의미 |
|---|---|
| **HTTP 200** | "결제 완료 · 주문 접수됨" — 돈은 이미 빠짐 (확정) |
| **SSE** | "재고 확보 성공 / 부족해서 취소됨" — 판정 ([OrderProcessingService.java:93](src/main/java/com/whale/order/domain/order/service/OrderProcessingService.java#L93), [:143](src/main/java/com/whale/order/domain/order/service/OrderProcessingService.java#L143)) |

선결제 구조라 "결제 확정"과 "재고 확정"이 원래 분리된 사건입니다. SSE는 Kafka 때문에 생긴 게 아니라 **선결제 때문에** 필요한 겁니다. Kafka를 빼도 SSE는 남습니다.

## 정리

| | Kafka OFF (현재 운영) | Kafka ON |
|---|---|---|
| 체감 응답 시간 | 락 대기 포함 → 피크에 최대 5초 | 사실상 동일 (브로커 홉만큼 +) |
| SSE 필요 여부 | **필요** | 필요 |
| 피크 시 다른 API | 같이 마비 | 살아 있음 |
| 재고 차감 실패 | 로그만, 수동 재처리 | 재시도 → DLT → 자동 보상 |

## 왜 구조적으로 at-least-once인가

Spring Kafka는 auto-commit을 끄고 **리스너가 정상 반환한 뒤** offset을 커밋합니다. 즉 `process() 성공 → offset 커밋` 사이에 항상 빈틈이 있습니다. 이 구간에서 프로세스가 죽거나 리밸런싱이 나면 같은 메시지가 다시 옵니다. 이 창은 원리적으로 없앨 수 없습니다.

## 중복에는 두 종류가 있고, 이 프로젝트는 하나만 막습니다

| **동시 중복** | 리밸런싱 중 좀비 컨슈머가 같은 파티션을 아직 잡고 있음 | ❌ 샙니다 |

### 동시 중복은 가드가 뚫립니다

`OrderProcessingService`에는 **`@Transactional`이 없습니다** (`OrderCancelService`·`OrderService`에는 있는데 여기만 없습니다). 그래서 `조회 → isStockDeducted 체크 → 차감 → save`가 원자적이지 않습니다. 같은 orderId가 두 스레드에 동시에 들어오면:

```
A, B 둘 다 order 로드 (stockDeducted=false, version=N)
  ↓ 둘 다 가드 통과
A: deductStock() → 분산 락 획득/해제 → 차감 성공
B: deductStock() → 락 대기 후 획득 → 차감 성공   ← 재고 2번 빠짐
  ↓ 분산 락은 "동시 실행"만 막지 "중복 실행"은 못 막음
A: save() → version N+1 ✅
B: save() → ObjectOptimisticLockingFailureException
  ↓ line 118 catch → handleFailure(reason="lock_conflict")
B: 자기 차감분 복구 (재고는 결과적으로 정상 ✅)
B: cancelOrder(orderId) ← 상태가 아직 PENDING이라 통과
  ↓
정상 처리된 주문이 취소 + 환불되고, SSE로 "주문 처리 실패" 발송 ❌
```

`Orders`의 `@Version`([Orders.java:31](src/main/java/com/whale/order/domain/order/entity/Orders.java#L31))이 lost update는 막아줍니다. 문제는 **그 뒤의 실패 처리 경로가 "내가 늦게 온 중복이다"와 "진짜 처리 실패다"를 구분하지 못한다**는 점입니다. 재고는 지켜지는데 주문이 잘못 취소됩니다.

## 왜 필요한가 — 두 가지 경로

**1) 락을 애초에 못 얻은 경우**
```java
if (!lock.tryLock(5, TimeUnit.SECONDS)) {
    throw new StockLockException("재고 처리 중입니다...");   // ← finally는 여전히 실행됨
}
```
`tryLock`이 `false`를 반환해도 `finally`는 돕니다. 가드가 없으면 소유하지 않은 락에 `unlock()`을 호출하게 됩니다. `InterruptedException` 경로도 마찬가지입니다.

**2) 락을 얻었다가 잃은 경우** — 질문에서 말한 *"권한을 이미 잃었거나"* 가 이쪽입니다.

`leaseTime` 인자를 생략해 watchdog 모드로 동작하는데([line 30-31](src/main/java/com/whale/order/domain/stock/service/StockLockFacade.java#L30-L31)), 긴 GC pause나 Redis 네트워크 단절로 watchdog이 갱신에 실패하면 30초 뒤 락이 자동 해제됩니다. 그 사이 다른 스레드가 같은 락을 잡을 수 있고, 이때 원래 스레드가 `unlock()`을 부르면 **남의 락을 푸는** 셈이 됩니다. `isHeldByCurrentThread()`는 Redis에 저장된 소유자(`{nodeId}:{threadId}`)를 조회해 확인하므로 이 경우 `false`를 반환하고 해제를 건너뜁니다.

## 가드가 없으면 실제로 뭐가 망가지는가

여기가 면접에서 한 번 더 들어오는 지점입니다. 단순히 "예외가 뜬다"가 아니라 **재시도 시맨틱이 바뀝니다.**

`finally`에서 던진 예외는 진행 중이던 예외를 **덮어씁니다**. 따라서:

```
가드 없음 → StockLockException이 IllegalMonitorStateException으로 교체
   ↓
OrderProcessingService의 catch (StockLockException) 매칭 실패   ← line 100
   ↓
catch (Exception e) 로 떨어짐                                  ← line 123
   ↓
handleFailure() → 재고 복구 + 주문 취소 + 결제 환불 + SSE "실패"
```

원래 의도는 [OrderProcessingService.java:100-112](src/main/java/com/whale/order/domain/order/service/OrderProcessingService.java#L100-L112) — 락 타임아웃은 **일시적 상태**이므로 rethrow해서 Kafka가 1초 간격 3회 재시도하고, 대부분 그 안에 성공합니다. 가드가 없으면 그 재시도 기회 없이 **곧바로 주문 취소·환불**로 직행합니다.

즉 이 `if` 한 줄은 예외 하나를 막는 게 아니라 **"일시적 실패"와 "영구적 실패"의 구분을 지키는** 장치입니다.

## 정직하게 말할 한계

`isHeldByCurrentThread()` 자체가 Redis 왕복이라 **check-then-act 갭**이 있습니다. 확인 직후 lease가 만료되면 여전히 `IllegalMonitorStateException`이 날 수 있습니다. 다만 Redisson의 `unlock()`은 내부 Lua 스크립트에서 소유권을 한 번 더 검증하므로, 이 가드는 "정상 케이스에서 예외를 없애는" 1차 방어이고 완전한 보장은 아닙니다.

완전히 막으려면 `finally` 안에서 `try { lock.unlock(); } catch (IllegalMonitorStateException ignored) {}` 로 감싸야 합니다. 다만 그건 원인을 삼켜버려 진단이 어려워지므로, 현재 방식(가드 + Redisson 내부 검증)이 일반적인 선택입니다.

## 답변용 요약

> `finally`에서 `isHeldByCurrentThread()`로 현재 스레드가 락 보유자인지 Redis에 확인한 뒤에만 `unlock()`을 호출합니다. `tryLock` 타임아웃으로 애초에 못 얻은 경우와, watchdog 갱신 실패로 lease가 만료돼 소유권을 잃은 경우를 모두 걸러냅니다.
>
> 이걸 두는 이유가 단순히 예외 회피는 아닙니다. `finally`의 예외는 진행 중이던 예외를 덮어쓰는데, 그러면 락 타임아웃을 알리는 `StockLockException`이 사라져서 상위 Consumer가 "일시적 실패 → Kafka 재시도" 대신 "처리 불가 → 주문 취소·환불"로 처리해버립니다. 재시도 가능한 실패를 재시도 가능한 상태로 유지하기 위한 장치입니다.
>
> 다만 확인과 해제 사이에 lease가 만료될 수 있어 완전한 보장은 아니고, 최종 방어는 Redisson `unlock()` 내부 Lua 스크립트의 소유권 검증입니다.

## 여기서 그냥 재시도하면 재고가 두 번 빠집니다

Kafka가 재전달하면 `process()`가 **처음부터** 다시 돕니다:

```
재시도: ① 아메리카노 차감 → 또 빠짐 ❌ (이미 아까 빠졌는데)
       ② 라떼 차감      → 또 빠짐 ❌
       ③ 케이크 차감    → 이번엔 성공
```

아메리카노와 라떼가 **2번씩** 차감됩니다. 그래서 rethrow 하기 전에 이번 시도에서 뺀 것만 되돌려서 **"아무것도 안 한 상태"로 원위치**시키는 겁니다.

```java
for (OrderItem item : deducted) {     // 아메리카노, 라떼만
    restoreWithRetry(orderId, storeId, item);   // 도로 채워넣음
}
throw e;                              // ← 이제 깨끗하니 재시도해도 안전
```

`deducted` 리스트가 존재하는 이유가 이겁니다. **"이번 시도에서 내가 건드린 것"만 정확히 되돌리기 위한 장부**입니다.

## `throw e;` 가 재시도를 일으키는 방식

Kafka는 **리스너가 정상적으로 끝나야** offset을 커밋합니다. 예외를 던지면 커밋하지 않고, 커밋 안 된 메시지는 아직 안 읽은 것으로 취급되어 1초 뒤 다시 옵니다.

```
throw e
  → OrderKafkaConsumer.consume()도 rethrow (line 32)
  → offset 커밋 안 함
  → 1초 뒤 같은 메시지 재전달 (FixedBackOff(1000L, 3))
  → 3번 다 실패하면 DLT → compensate() → 주문 취소
```

즉 `throw e`는 "실패했다"가 아니라 **"Kafka야, 이거 다시 줘"** 라는 신호입니다.

## 왜 취소가 아니라 재시도인가

바로 아래 `catch (IllegalStateException)`(재고 부족)은 정반대로 **즉시 주문을 취소**합니다. 둘을 나눈 기준은 **1초 뒤에 다시 해보면 될 일인가**입니다.

| | 락 획득 실패 | 재고 부족 |
|---|---|---|
| 원인 | 지금 그 메뉴에 주문이 몰려 순서를 못 잡음 | 물건이 없음 |
| 1초 뒤 재시도하면? | **대개 성공** (앞사람 처리 끝남) | 여전히 없음 |
| 처리 | 되돌리고 rethrow → 재시도 | 되돌리고 즉시 취소·환불 |

락 타임아웃은 **일시적 혼잡**이지 실패가 아닙니다. 여기서 바로 취소해버리면 피크 시간에 멀쩡한 주문이 무더기로 취소·환불됩니다.

## Redis 안에 실제로 뭐가 들어있나

Redisson은 락을 **Hash**로 저장합니다. `tryLock()`이 성공한 직후 Redis를 들여다보면:

```
> HGETALL stock:lock:5:42

1) "a3f8b2c1-...-9d4e:52"    ← field : {노드UUID}:{스레드ID}  = 소유자 이름표
2) "1"                       ← value : 재진입 횟수
```

`isHeldByCurrentThread()`는 이 Hash에 **내 이름표(`{내 노드UUID}:{현재 스레드ID}`)가 필드로 존재하는지** 확인하는 것입니다. 대략 `HEXISTS stock:lock:5:42 "a3f8b2c1-...:52"` 한 방입니다.

## `false`가 나오는 세 가지 경우

| 상황 | 왜 |
|---|---|
| `tryLock`이 5초 타임아웃으로 실패 | 애초에 이름표를 못 적음 |
| watchdog 갱신이 끊겨 lease 만료 | Redis가 키를 지워버림 → 이름표 소멸 |
| 다른 스레드가 잡고 있음 | 이름표는 있는데 **내 것이 아님** |

세 번째가 핵심입니다. 락은 **스레드 단위 소유**라서, 같은 JVM 안의 옆 스레드가 잡고 있어도 나에게는 `false`입니다. `isLocked()`(누구든 잡고 있냐)와 `isHeldByCurrentThread()`(내가 잡고 있냐)가 다른 이유입니다.

```java
lock.isLocked()               // 누군가 잡고 있으면 true — 남의 락이어도 true
lock.isHeldByCurrentThread()  // 내가 잡고 있을 때만 true      ← unlock 판단은 이걸로
```

`unlock()`은 **소유자만** 호출할 수 있으니 `isLocked()`로 판단하면 안 되고, 반드시 `isHeldByCurrentThread()`여야 합니다.

## 재진입 카운트 이야기

value의 `"1"`은 같은 스레드가 락을 **몇 겹** 잡았는지입니다. 같은 스레드가 `lock()`을 두 번 부르면 `2`가 되고, `unlock()`을 두 번 불러야 완전히 풀립니다. `isHeldByCurrentThread()`는 이 값이 1 이상이면 `true`입니다.

지금 코드는 [StockLockFacade.deductStock](src/main/java/com/whale/order/domain/stock/service/StockLockFacade.java#L27)에서 락을 중첩해서 잡지 않으니 항상 0 아니면 1입니다.

## 주의할 점

이 호출은 **로컬 변수 확인이 아니라 Redis 왕복**입니다. `finally`마다 네트워크 호출이 한 번씩 더 나가고, 확인한 그 순간과 `unlock()` 하는 순간 사이에 lease가 만료될 수도 있습니다 — 앞서 말한 check-then-act 갭이 여기서 생깁니다.

## 2단계 — 어떤 상황을 막는지 (여기까지 말하면 좋음)

> 가드가 필요한 경우가 두 가지입니다.
>
> 첫째는 **애초에 락을 못 얻은 경우**입니다. `tryLock(5, TimeUnit.SECONDS)`가 `false`를 반환해서 예외를 던져도 `finally`는 실행되기 때문에, 가드가 없으면 소유하지 않은 락에 `unlock()`을 호출하게 됩니다.
>
> 둘째는 **얻었다가 잃은 경우**입니다. 저희는 `leaseTime`을 생략해서 watchdog 자동 갱신 모드를 쓰는데, 긴 GC pause나 Redis 네트워크 단절로 갱신이 끊기면 락이 만료됩니다. 그 사이 다른 스레드가 같은 락을 잡을 수 있고, 이때 원래 스레드가 `unlock()`을 부르면 남의 락을 푸는 셈이 됩니다. `isHeldByCurrentThread()`가 이 경우도 걸러줍니다.

## 3단계 — 차별화 포인트 (여기가 가산점)

> 그런데 이 가드를 둔 이유가 단순히 예외를 안 나게 하려는 것만은 아닙니다.
>
> `finally`에서 발생한 예외는 **진행 중이던 예외를 덮어씁니다.** 저희 구조에서는 락 타임아웃 시 `StockLockException`을 던지고, 상위의 Kafka Consumer가 그걸 받아 "일시적 실패"로 판단해 1초 간격 3회 재시도를 겁니다. 그런데 `finally`에서 `IllegalMonitorStateException`이 터지면 원래 예외가 사라져서, Consumer가 이걸 "알 수 없는 오류"로 처리해 **재시도 없이 곧바로 주문 취소·결제 환불**로 넘어갑니다.
>
> 즉 이 한 줄은 예외 하나를 막는 게 아니라, **"재시도하면 될 실패"를 재시도 가능한 상태로 유지하는** 장치입니다. 피크 시간에 멀쩡한 주문이 무더기로 취소되는 걸 막습니다.

## 1단계 — 핵심 (이것만으로 정답)

> **조회와 저장 사이의 갭을 없앤 게 아니라, 판정 주체를 조회가 아닌 원자적 쓰기로 옮겼습니다.**
>
> 조회(`getResult`)는 이미 완료된 요청을 빠르게 걸러내는 **fast path 최적화**일 뿐이고, 실제 관문은 그다음의 `markProcessing()`입니다.
>
> ```java
> public boolean markProcessing(String key) {
>     RBucket<String> bucket = redissonClient.getBucket(KEY_PREFIX + key);
>     return bucket.setIfAbsent(PROCESSING_MARKER, PROCESSING_TTL);
> }
> ```
>
> 이건 Redis의 `SET key value NX EX 60` 단일 명령입니다. Redis는 명령을 **단일 스레드로 직렬 처리**하므로, 0.001초 간격이든 완전히 동시든 두 요청은 Redis 명령 큐에서 순서가 정해지고 **정확히 하나만 `true`를 받습니다.** 읽고 나서 쓰는 게 아니라, 쓰기 한 번으로 판정이 끝나기 때문에 read-write 갭 자체가 판정에 영향을 주지 않습니다.

## 2단계 — 두 요청이 실제로 어떻게 갈리는지

> 동일 키로 A, B가 동시에 들어오면 이렇게 흐릅니다.
>
> ```
> A, B 둘 다 getResult() → null        ← 갭이 있어도 여기선 아무것도 결정 안 함
>      ↓
> A: markProcessing() → true            ← Redis가 직렬화, 선착순 하나만
> B: markProcessing() → false
>      ↓
> A: 결제 진행 → saveResult(key, 응답)
> B: getResult() 재확인 → 있으면 그 결과 반환, 없으면 409 DuplicateRequestException
> ```
>
> B가 예외를 던지기 전에 `getResult()`를 **한 번 더** 확인하는 이유는, A가 그 찰나에 이미 완료했을 수 있기 때문입니다. 그 경우 B에게 에러 대신 A의 결과를 그대로 돌려줘서 "같은 요청 = 같은 응답"이라는 멱등성 계약을 지킵니다.

## 3단계 — TTL 설계 (가산점)

> 이 구조의 또 다른 핵심은 `SET NX`에 **TTL이 함께 붙는다**는 점입니다. PROCESSING 마커에 60초 TTL이 걸려 있어서, A가 처리 도중 서버가 죽어 키를 지우지 못해도 60초 뒤 자동 만료됩니다. **죽은 PROCESSING 키가 그 결제를 영구히 잠그는 상황이 없습니다.**
>
> 원래는 PostgreSQL `ON CONFLICT` 기반이었는데, 거기선 "30초 넘게 PROCESSING이면 죽은 것으로 보고 재획득"하는 타임아웃 감지 로직이 필요했고, **그 감지와 재획득 사이에 다시 race가 생기는** 문제가 있었습니다. Redis `SET NX EX`는 원자성과 만료를 한 명령이 동시에 제공해서 그 로직 자체를 없앨 수 있었습니다.
>
> 정상 실패(PG 오류 등) 시에는 `catch` 블록에서 키를 즉시 삭제해 클라이언트가 바로 재시도할 수 있게 합니다.

## 짚어둘 점 — 60초 안에 "한 잔 더"가 막힙니다

키가 **장바구니 내용 해시**라서, 결제 성공 후 60초 안에 **똑같은 구성으로 다시 주문**하면 캐시된 이전 응답이 반환됩니다. 새 주문이 생성되지 않는데 사용자 화면에는 결제 성공으로 보입니다.

## 현실에서 얼마나 문제인가

카페 시나리오라 걸릴 만합니다 — 일행 것을 따로 결제하거나, 마시고 나서 한 잔 더 시키는 경우. 다만 대부분은 수량을 2로 담거나(다른 키), 1분이 지나거나(TTL 만료), 옵션이 달라서(다른 키) 자연히 비켜갑니다.

이게 **콘텐츠 기반 멱등키의 구조적 약점**입니다. "같은 내용 = 같은 요청"으로 간주하는데, 현실에는 **의도적으로 같은 내용을 두 번 보내는 경우**가 존재합니다. 그래서 실무에서는 클라이언트가 `Idempotency-Key` 헤더를 **요청마다 새로 발급**하는 방식을 씁니다 — 그러면 "재전송"과 "새 주문"을 내용이 아니라 키 발급 주체가 구분해줍니다.

## 지금 구조에서 고치는 방법

| 방법 | 효과 |
|---|---|
| TTL을 60초 → 10초 정도로 축소 | 간단. 네트워크 재시도 보호는 유지되면서 오탐 창이 줄어듦 |
| 키에 `orderId` 시퀀스나 클라이언트 요청 ID 추가 | 근본 해결. 프런트 수정 필요 |
| 클라이언트 발급 `Idempotency-Key` 헤더로 전환 | 표준 방식. 가장 깔끔하지만 작업량 큼 |

TTL 축소가 비용 대비 효과가 가장 좋습니다. 네트워크 재시도는 보통 수 초 안에 일어나므로 10~15초면 충분하고, "한 잔 더" 오탐은 거의 사라집니다.

면접에서는 이 트레이드오프를 **알고 선택했다**고 말하는 게 중요합니다 — *"콘텐츠 기반이라 60초 내 완전 동일 주문은 재전송으로 오인됩니다. 결제 중복보다는 낫다고 판단해 감수했고, 실서비스라면 클라이언트 발급 키로 전환할 계획입니다"* 정도면 충분합니다.

## 키 하나가 가질 수 있는 상태는 3가지

```
idem:{sha256}  →  ① 없음              (처음 오는 요청)
                  ② "__PROCESSING__"  (다른 요청이 처리 중)
                  ③ {"paymentId":...}  (이미 완료됨, 60초 캐시)
```

## 검사 흐름 — 왜 두 번 보는가

[PaymentService.java:129-141](src/main/java/com/whale/order/domain/payment/service/PaymentService.java#L129-L141)
```java
PaymentResponse cached = idempotencyService.getResult(key, PaymentResponse.class);   // ①
if (cached != null) return cached;

if (!idempotencyService.markProcessing(key)) {                                        // ②
    PaymentResponse completed = idempotencyService.getResult(key, PaymentResponse.class);  // ③
    if (completed != null) return completed;
    throw new DuplicateRequestException("동일한 요청이 처리 중입니다...");
}
```

핵심은 `getResult()`가 **"없음"과 "PROCESSING"을 둘 다 `null`로 돌려준다**는 점입니다:

[IdempotencyService.java:53](src/main/java/com/whale/order/global/idempotency/IdempotencyService.java#L53)
```java
if (value == null || PROCESSING_MARKER.equals(value)) return null;
```

그래서 `getResult()` 하나로는 "처음 온 요청"인지 "처리 중"인지 구분할 수 없습니다. **그 구분은 `markProcessing()`이 합니다** — `SET NX`가 실패했다는 건 키가 이미 있다는 뜻이니까요.

## 상태별 결과

| 키 상태 | ① getResult | ② markProcessing | ③ 재확인 | 최종 |
|---|---|---|---|---|
| 없음 | null | **true** (선점) | — | 결제 진행 |
| PROCESSING | null | false | null | **409** DuplicateRequest |
| 완료(JSON) | 객체 | — | — | **200** 캐시 반환 |
| ②와 ③ 사이에 완료됨 | null | false | 객체 | **200** 캐시 반환 |

마지막 행이 ③이 존재하는 이유입니다. `markProcessing`이 실패한 그 찰나에 앞 요청이 결제를 끝냈을 수 있어서, 에러를 던지기 전에 한 번 더 확인해 결과가 있으면 그걸 돌려줍니다. **"처리 중"으로 오판해 사용자에게 불필요한 에러를 주지 않기 위한 재확인**입니다.

## 혹시 "처리 대기중"이 주문 상태를 뜻한 거라면

멱등 검사는 **DB의 주문 상태(`OrderStatus.PENDING` / `PREPARING` / `COMPLETED`)를 전혀 보지 않습니다.** 오직 Redis 키의 존재 여부와 값만 봅니다.

- 결제 후 **70초** — 주문 상태와 무관하게 키가 만료됐으니 동일 요청도 **새 주문으로 통과**

즉 판단 기준은 "주문이 어디까지 진행됐나"가 아니라 **"마지막 동일 요청으로부터 60초가 지났나"** 뿐입니다. 주문 도메인과 완전히 분리된 별개 계층입니다.

## 값 — 시간에 따라 두 번 바뀝니다

```

    (키 소멸)
```

두 번째 값은 [PaymentResponse](src/main/java/com/whale/order/domain/payment/dto/PaymentResponse.java) record를 `ObjectMapper`로 직렬화한 JSON입니다. 필드가 그대로 들어갑니다 — `paymentId`, `orderId`, `amount`, `method`, `status`, `externalTxId`, `queuePosition`.

## 타임라인

```
결제 요청 도착
   │
   ├─ SET idem:9f86... "__PROCESSING__" NX EX 60      ← 선점
   │
   ├─ (PG 호출, 주문/결제 저장 ...)
   │
```

`markProcessing`은 `SET NX`(없을 때만), `saveResult`는 그냥 `SET`(무조건 덮어쓰기)입니다. 그래서 PROCESSING 마커가 결과 JSON으로 **교체**됩니다.

## 함정 — redis-cli로 보면 깨끗한 텍스트가 아닙니다

[RedissonConfig.java](src/main/java/com/whale/order/global/config/RedissonConfig.java)에서 코덱을 지정하지 않아 Redisson 기본값을 씁니다. Redisson 3.27.2의 기본 코덱은 **Kryo5Codec**이라, `RBucket<String>`에 넣은 문자열도 바이너리로 인코딩되어 저장됩니다.

```bash
> GET idem:9f86d081...
"\x01\x0e__PROCESSING__"     # ← 앞에 Kryo 헤더 바이트가 붙음
```

즉 **JSON 텍스트를 Kryo가 한 번 더 감싼** 이중 구조입니다. 값 자체는 대부분 읽히지만 순수 문자열은 아닙니다.

이게 헷갈리는 이유는 같은 프로젝트에서 Redis 클라이언트를 **두 개** 쓰기 때문입니다:

| 용도 | 클라이언트 | 저장 형태 |
|---|---|---|
| 장바구니 (`cart:*`), 주문 대기열 (`order:queue`) | `StringRedisTemplate` | **순수 문자열** — redis-cli로 그대로 읽힘 |
| 멱등성 (`idem:*`), 분산 락 (`stock:lock:*`) | Redisson `RBucket`/`RLock` | **Kryo 바이너리** |

장바구니는 `HGETALL cart:1001` 하면 JSON이 그대로 보이는데 멱등 키는 안 그래서, 디버깅할 때 "값이 왜 이래?" 하고 당황하기 쉽습니다. 버그는 아니고 클라이언트 차이입니다.

굳이 맞추고 싶다면 `RedissonConfig`에 `config.setCodec(new StringCodec())`를 주면 됩니다. 다만 락 등 다른 Redisson 구조체에도 함께 적용되니 지금 상태로 두는 게 무난합니다.

## 실제 선택 기준

| 화면 | 실무 선택 | 이유 |
|---|---|---|
| 어드민 테이블 (1 2 3 … 페이지 번호) | `Page` | 총 개수·마지막 페이지가 UI에 필요 |
| 모바일 앱 피드 · 무한 스크롤 | **커서 기반** | 사실상 표준 |
| 자동완성 · 인기 top 10 | 그냥 `LIMIT` | 페이징 개념 자체가 불필요 |

`Slice`는 "count 쿼리 없는 offset 페이징"인데, **실무에서 비중이 가장 애매합니다.** 무한 스크롤에 쓰려고 만든 건데 정작 무한 스크롤은 커서로 가는 경우가 많아서요. 트래픽이 크지 않은 내부 서비스에서 간편하게 쓰는 정도입니다.

## offset 방식(`Page`/`Slice`)의 두 가지 약점

**1) 깊은 페이지가 느립니다**
```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```
DB는 10만 행을 **읽고 버린 뒤** 20행을 줍니다. 페이지가 깊어질수록 선형으로 느려집니다.

**2) 중복·누락이 생깁니다** — 이게 더 치명적입니다

1페이지를 본 사이에 새 주문이 3건 들어오면, 2페이지를 요청할 때 전체 목록이 3칸 밀립니다. → **1페이지 마지막 항목들이 2페이지에 또 나옵니다.** 반대로 삭제되면 건너뜁니다. 주문·알림처럼 계속 쌓이는 데이터에서 자주 겪는 버그입니다.

## 커서 방식

"몇 번째부터"가 아니라 **"이 값 다음부터"** 로 요청합니다.

```sql
SELECT * FROM orders
WHERE order_id < :lastOrderId        -- 클라이언트가 받은 마지막 값
ORDER BY order_id DESC
LIMIT 20;
```

- 인덱스를 그대로 타서 **몇 페이지를 넘겨도 속도가 일정**합니다
- 새 데이터가 끼어들어도 기준점이 값이라 중복·누락이 없습니다
- 대신 **임의 페이지 점프가 불가능**하고(5페이지로 바로 못 감), 정렬 기준이 사실상 고정됩니다

응답은 보통 이렇게 나갑니다:
```json
{ "content": [...], "nextCursor": 982, "hasNext": true }
```

## `Page`의 숨은 비용 — count 쿼리

`Page`는 매 요청마다 `SELECT count(*)`를 한 번 더 날립니다. 데이터가 많아지면 **본 쿼리보다 count가 더 느린** 경우가 흔합니다. 그래서 큰 서비스들은 총 개수를 아예 안 보여주거나 "1,000+" 같은 근사치로 처리합니다(GitHub 검색 결과가 대표적입니다).

정렬·필터가 복잡한 어드민 화면이라면 Querydsl로 count 쿼리를 따로 최적화하거나, `PageableExecutionUtils`로 마지막 페이지에서 count를 생략하는 방식을 씁니다.

## 왜 HHH000104가 발생하는지 (답변 앞부분에 깔 내용)

> 1:N을 조인하면 결과 행이 자식 수만큼 뻥튀기됩니다. 주문 1건에 항목이 3개면 3행이 되죠. 이 상태에서 `LIMIT 20`을 걸면 DB는 **주문 20건이 아니라 조인 결과 20행**을 자르기 때문에, 20번째 주문의 항목 일부가 잘려 나간 불완전한 엔티티가 만들어집니다.
>
> Hibernate는 이 부정확성을 허용할 수 없어서 **LIMIT을 SQL에서 빼고 전체를 메모리로 올린 뒤 애플리케이션에서 자릅니다.** 그게 HHH000104 경고이고, 데이터가 수십만 건이면 그대로 OOM입니다.

> "제 프로젝트에서는 HHH000104를 실제로 만나지는 않았습니다. 주문 목록 API에 페이징을 아직 넣지 않았기 때문입니다. 다만 컬렉션 Fetch Join과 페이징을 함께 쓰면 안 된다는 건 인지하고 있어서, **목록 조회 쿼리에서는 `store`·`member` 같은 ToOne 연관만 Fetch Join하고 `orderItems` 컬렉션은 지연 로딩으로 두는 원칙**을 지켰습니다. 컬렉션을 조인하는 건 주문 상세 단건 조회 하나뿐입니다.
>
> 그런데 이 질문을 받고 코드를 다시 보니 문제가 하나 보였습니다. 컬렉션을 지연 로딩으로 남겨두면 그다음에 N+1이 오는데, **`default_batch_fetch_size`를 설정하지 않아서 그게 그대로 발생하고 있었습니다.** 주문 20건 조회에 40~60개 쿼리가 나가는 구조였습니다.
>
> 그래서 지금은 `default_batch_fetch_size: 100`을 적용해서 컬렉션 로딩이 `IN` 절로 묶이게 했고, 주문 목록에는 커서 기반 페이징을 넣었습니다. 컬렉션을 조인하지 않으니 페이징이 DB 레벨에서 정상 동작하고, 배치 페치로 쿼리 수는 상수로 유지됩니다."

**단, 마지막 문단은 실제로 적용한 뒤에만 말해야 합니다.**

## 그래서 — 지금 고치면 저 답변을 그대로 쓸 수 있습니다

작업량이 작습니다.

**1) 한 줄 설정** (`application.yaml`의 `hibernate` 아래)
```yaml

```
이것만으로 `orderItems`와 `menu` 로딩이 `WHERE order_id IN (?, ?, ... )` 로 묶여 쿼리 수가 **N+1 → 3개 내외**로 떨어집니다. 코드 변경 없습니다.

**2) 목록에 페이징 추가** — 컬렉션을 조인하지 않으니 `Pageable`을 그냥 붙이면 DB 레벨에서 정상 동작합니다

**3) (선택) 어드민 목록은 DTO 직접 조회** — Querydsl이 이미 스택에 있으니, 어드민 목록처럼 화면 전용 데이터는 엔티티를 거치지 않고 DTO로 바로 뽑는 방식도 답변에 넣을 수 있습니다.

## 무엇이 달라지는가

주문 20건을 조회할 때:

```
[적용 전]
SELECT ... FROM orders o JOIN store ...                    1회
SELECT ... FROM order_item WHERE order_id = ?              × 20회
SELECT ... FROM menu WHERE menu_id = ?                     × 항목 수만큼
                                                    ─────────────
                                                    40~60 쿼리

[적용 후]
SELECT ... FROM orders o JOIN store ...                    1회
SELECT ... FROM order_item WHERE order_id IN (?,?,...,?)   1회
SELECT ... FROM menu WHERE menu_id IN (?,?,...,?)          1회
                                                    ─────────────
                                                    3 쿼리
```

100은 `IN` 절에 한 번에 묶는 최대 개수입니다. 주문이 250건이면 `IN` 쿼리가 3번 나뉘어 나갑니다. 페이지 크기를 20~50으로 잡을 계획이니 100이면 항상 한 방에 묶입니다.

`orderItems` 컬렉션뿐 아니라 **ToOne 프록시(`menu`, `member`)에도 함께 적용**되는 게 이 설정의 장점입니다. `@BatchSize`를 엔티티마다 붙이는 것과 달리 전역으로 한 번에 해결됩니다.

## 왜 두 개가 필요한가

`createdAt`만으로 자르면 **같은 시각에 생성된 주문**에서 문제가 생깁니다:

```
14:03:22.481  주문 #982
14:03:22.481  주문 #981   ← 페이지 경계가 여기라면?
14:03:22.481  주문 #980
```

- `createdAt < 14:03:22.481` → #981, #980이 **통째로 누락**
- `createdAt <= 14:03:22.481` → #982가 **다음 페이지에 또 나옴**

어느 쪽도 맞지 않습니다. 그래서 유일한 값(`orderId`)을 붙여 **전순서(total order)** 를 만듭니다.

## 조건식 — JPQL

개념적으로는 튜플 비교입니다:
```
(createdAt, orderId) < (:cursorCreatedAt, :cursorOrderId)
```

그런데 **JPQL은 튜플 비교를 지원하지 않아서** 펼쳐 써야 합니다:

```java
@Query("SELECT o FROM Orders o JOIN FETCH o.store " +
       "WHERE o.member.memberId = :memberId " +
       "  AND (o.createdAt < :cursorCreatedAt " +
       "       OR (o.createdAt = :cursorCreatedAt AND o.orderId < :cursorOrderId)) " +
       "ORDER BY o.createdAt DESC, o.orderId DESC")
List<Orders> findNextPageByMemberId(@Param("memberId") Long memberId,
                                    @Param("cursorCreatedAt") LocalDateTime cursorCreatedAt,
                                    @Param("cursorOrderId") Long cursorOrderId,
                                    Pageable pageable);
```

**가장 흔한 버그가 괄호입니다.** `memberId` 조건과 커서 조건을 `AND`로 묶을 때 커서 쪽 `OR` 전체를 괄호로 감싸지 않으면, `A AND B OR C`가 되어 **남의 주문까지 조회됩니다.** 위 코드의 바깥 괄호가 그 방어입니다.

`ORDER BY`도 반드시 `createdAt DESC, orderId DESC` 두 개를 다 써야 합니다. WHERE 조건과 정렬 순서가 어긋나면 커서가 깨집니다.

## PostgreSQL이라면 더 나은 방법이 있습니다

Postgres는 **행 값 비교(row-value comparison)** 를 네이티브로 지원하고, 옵티마이저가 이걸 복합 인덱스에 깔끔하게 매핑합니다:

```sql
WHERE member_id = ? AND (created_at, order_id) < (?, ?)
ORDER BY created_at DESC, order_id DESC
LIMIT ?
```

위의 `OR` 형태는 옵티마이저가 인덱스 range scan으로 못 풀고 필터로 처리하는 경우가 있어서, 데이터가 커지면 성능 차이가 납니다. JPQL로는 표현이 안 되니 두 가지 선택지가 있습니다.

**네이티브 쿼리**
```java
@Query(value = """
        SELECT * FROM orders
        WHERE member_id = :memberId AND (created_at, order_id) < (:cursorCreatedAt, :cursorOrderId)
        ORDER BY created_at DESC, order_id DESC
        LIMIT :size
        """, nativeQuery = true)
List<Orders> findNextPage(...);
```
단점: `JOIN FETCH`를 못 써서 `store` 조회가 별도 쿼리로 나갑니다. (배치 페치가 있으니 1회로 묶이긴 합니다.)

**Querydsl** — 이미 의존성이 있습니다([build.gradle:46](build.gradle#L46))
```java
BooleanExpression cursorCondition = Expressions.booleanTemplate(
        "({0}, {1}) < ({2}, {3})",
        order.createdAt, order.orderId, cursorCreatedAt, cursorOrderId);

queryFactory.selectFrom(order)
        .join(order.store).fetchJoin()
        .where(order.member.memberId.eq(memberId), cursorCondition)
        .orderBy(order.createdAt.desc(), order.orderId.desc())
        .limit(size + 1)
        .fetch();
```
`fetchJoin()`도 되고 행 값 비교도 쓸 수 있어서 이게 가장 낫습니다. 커서가 없는 첫 페이지는 `cursorCondition`을 `null`로 넘기면 Querydsl이 알아서 조건을 뺍니다 — 쿼리 메서드를 두 개로 나눌 필요도 없어집니다.

## 인덱스는 필수입니다

복합 커서가 실제로 필요해지는 건 이런 경우입니다:

| 상황 | 이유 |
|---|---|
| 정렬 기준이 PK와 무관 (인기순·가격순·평점순) | 값이 중복되고 PK 순서와 무관 |
| PK가 UUID | 생성 순서를 담지 않음 |
| 여러 테이블을 합친 피드 | 단일 시퀀스가 없음 |

> "지금은 `orderId`가 자동 증가 PK라 단일 커서로 충분합니다. 다만 정렬 기준이 생성 시각이나 인기순처럼 중복 가능한 값이 되면 동률 구간에서 누락·중복이 생기므로, `(createdAt, orderId)` 복합 커서로 전순서를 만들고 `(created_at, order_id) < (?, ?)` 행 값 비교와 복합 인덱스를 함께 씁니다."

## 인덱스 관련 한 가지

`@Index`에 `DESC`를 넣지 않았습니다. PostgreSQL은 오름차순 B-tree 인덱스를 **역방향 스캔**할 수 있고, 정렬이 두 컬럼 모두 DESC로 방향이 일치하므로 오름차순 인덱스로 충분합니다. `ddl-auto: update`인 dev·prod에서는 다음 기동 시 자동 생성되고, 테스트에서 `create-drop`으로 실제 생성되는 것도 확인됐습니다.

## 2) 핵심 — "재처리"가 아니라 "보상"입니다

면접관은 *재처리(retry)* 를 물었지만, 이 프로젝트의 DLT 컨슈머는 **주문을 다시 처리하지 않습니다.** `compensate()`가 하는 일은 [OrderProcessingService.java:189-198](src/main/java/com/whale/order/domain/order/service/OrderProcessingService.java#L189-L198):

```
compensate(orderId)
  → orderCancelService.cancelOrder(orderId)   // 주문 CANCELLED + 결제 환불
  → SSE "주문 처리에 실패했습니다"
```

**재시도가 아니라 취소·환불로 확정**합니다. 이건 실수가 아니라 선결제 구조에서 나온 선택입니다:

- 이미 결제가 완료된 상태라 **불확실한 상태를 오래 끄는 게 사용자에게 더 나쁩니다**
- DLT까지 왔다는 건 1초 간격 3회 재시도가 모두 실패했다는 뜻이고, 원인이 락 타임아웃이든 재고 부족이든 더 기다린다고 나아진다는 보장이 없습니다
- 사용자 입장에선 "언젠가 될지도 모르는 대기"보다 **즉시 환불 + 재주문**이 명확합니다

그래서 **DLT를 "나중에 재처리할 큐"가 아니라 "자동 보상 트리거"로 쓴다**는 게 정확한 설명입니다. 이렇게 답하면 설계 의도를 이해하고 있다는 신호가 됩니다.

## 3) Out-of-order — 이 구조에선 성립하지 않습니다

질문의 시나리오는 "실패 메시지가 DLT를 거쳐 늦게 처리되면서 후속 정상 메시지를 추월당한다"인데, 여기엔 **같은 엔티티에 대한 이벤트가 여러 개**라는 전제가 깔려 있습니다. 이 프로젝트는 그렇지 않습니다.

| 방어선 | 내용 |
|---|---|
| **토픽이 하나** | `order-created` 뿐입니다. 주문 하나당 발행되는 이벤트도 **딱 1건**이라 추월당할 "후속 이벤트"가 존재하지 않습니다 |
| **파티션 키 = orderId** | [OrderKafkaProducer.java:24](src/main/java/com/whale/order/domain/order/service/OrderKafkaProducer.java#L24) — 같은 주문은 항상 같은 파티션으로 가므로, 이벤트가 늘어나더라도 파티션 내 순서가 보장됩니다 |
| **상태 전이는 Kafka 미경유** | PENDING → PREPARING → COMPLETED는 어드민 API가 DB에 동기 반영하고 SSE로 직접 푸시합니다. 메시징 계층을 타지 않으니 순서 문제 자체가 없습니다 |
| **서로 다른 주문 간 순서는 무의미** | 주문 #1001과 #1002의 처리 순서는 비즈니스적으로 아무 의미가 없습니다 |

즉 **"순서를 보장하는 장치를 만들었다"가 아니라 "순서 문제가 생기지 않는 구조로 설계했다"** 가 정답입니다.

## 4) 대신 이 프로젝트엔 다른 경합이 있습니다 (여기가 가산점)

이걸 먼저 꺼내면 훨씬 깊이 있어 보입니다.

락 타임아웃으로 DLT까지 가는 데 최대 **15초 이상**(`tryLock` 5초 × 3회 + backoff) 걸립니다. 그동안 주문은 `PENDING` 상태로 **어드민 주문 목록에 노출**되어 있습니다.

```
주문 처리 실패 → 재시도 중 (주문은 PENDING)
   │
   ├─ [어드민] "제조 시작" 클릭 → status = PREPARING
   │
   └─ [DLT] compensate() → cancelOrder() → order.cancel()
           └─ Orders.cancel() 은 PENDING 에서만 허용 → IllegalStateException
                └─ consumeDlt 의 catch 가 삼킴 → 로그만
```

결과: **재고는 차감되지 않았는데 주문은 PREPARING, 결제는 SUCCESS로 남는 유령 주문**이 생깁니다. 매장은 만들 재고가 없는 주문을 접수한 상태가 됩니다.

이건 out-of-order라기보다 **동기 경로(어드민 API)와 비동기 경로(DLT 보상)의 경합**인데, 질문의 문제의식과 같은 뿌리입니다. 막으려면 `stockDeducted=false`인 주문은 어드민이 접수하지 못하게 막거나, `compensate`가 PREPARING 상태도 취소할 수 있도록 `cancelByAdmin()` 경로를 쓰면 됩니다.

## 답변 스크립트

> **DLT 소비 방식**은 별도 컨슈머 그룹(`whale-order-dlt`)이 구독하는 자동 컨슈머입니다. 배치나 수동이 아니라 즉시 소비합니다.
>
> 다만 정확히 말씀드리면 **재처리가 아니라 보상**입니다. 선결제 구조라 이미 돈이 빠진 상태인데, 1초 간격 3회 재시도가 모두 실패한 시점에서 더 기다리게 하는 것보다 즉시 취소·환불하고 재주문을 유도하는 게 사용자에게 명확하다고 판단했습니다. 그래서 DLT를 "나중에 다시 처리할 큐"가 아니라 "자동 보상 트리거"로 사용합니다.
>
> **순서 문제**는 별도 장치를 두지 않았습니다. 만들지 않은 게 아니라 필요가 없는 구조여서입니다. 토픽이 `order-created` 하나뿐이고 주문 하나당 이벤트가 1건이라 추월당할 후속 이벤트가 없습니다. 주문 상태 전이는 어드민 API가 DB에 동기 반영하고 SSE로 직접 푸시해서 메시징 계층을 타지 않습니다. 서로 다른 주문 사이의 순서는 비즈니스적으로 의미가 없고요.
>
> 다만 이벤트 종류가 늘어나면 문제가 생깁니다. 그래서 발행 시 **파티션 키를 `orderId`로 잡아뒀습니다.** 같은 주문의 이벤트는 항상 같은 파티션에 떨어져 순서가 보장되니, `payment-*`·`stock-*` 토픽으로 확장하더라도 주문 단위 순서는 유지됩니다. 그 위에 엔티티의 상태 머신 가드(`Orders.cancel()`이 PENDING에서만 허용하는 식)로 늦게 도착한 이벤트를 거르는 방식을 함께 쓸 계획입니다.
>
> 실제로 순서보다 먼저 해결해야 할 경합을 하나 발견했는데 — DLT 보상이 도는 15초 사이에 어드민이 그 주문을 접수하면 상태가 PREPARING으로 바뀌어서 보상이 실패합니다. 이건 개선 대상으로 보고 있습니다.

## 이 숫자가 실제로 바꾸는 것

`IN` 절 하나에 넣을 최대 개수입니다. 지연 로딩 대상이 N개일 때:

```
쿼리 수 = ceil(N / batch_fetch_size)
```

| batch size | 주문 20건 조회 시 `order_item` 쿼리 |
|---|---|
| 미설정(1) | 20회 ← N+1 |
| 10 | 2회 |
| 20 | 1회 |
| 100 | 1회 |
| 1000 | 1회 |

**20을 넘어가면 이 프로젝트의 기본 페이지(20건)에선 차이가 없습니다.** 100이 20보다 나은 점은 없습니다.

## 그럼 왜 20이 아니라 100인가

`orderItems`만 보면 20으로 충분한데, **`menu` 프록시**가 다릅니다.

주문 20건 × 항목 평균 2~3개 = `menuId` 40~60개(중복 제거 전). 여기서 20이면 3회로 쪼개지고, 100이면 1회입니다. 그래서 **"페이지 크기보다 넉넉하게"** 잡을 이유가 있습니다.

다만 정직하게 짚으면 — **상한인 100건 페이지에서는 100도 한 방이 아닙니다.** `menu`가 200~300개면 2~3회로 나뉩니다. "항상 한 번에 묶인다"는 건 기본 페이지(20건) 기준일 때만 맞습니다.

## 무한정 키우면 안 되는 이유

| 이유 | 설명 |
|---|---|
| **SQL 파싱/플래닝 비용** | `IN (?, ?, ... × 1000)` 은 파싱과 실행계획 수립 자체가 무거워집니다 |
| **PreparedStatement 캐시 오염** | Hibernate는 배치 크기별로 다른 SQL을 생성합니다. 최대치가 크면 SQL 변종이 늘어 캐시 히트율이 떨어집니다 |
| **영속성 컨텍스트 메모리** | 한 번에 로드되는 엔티티 수가 그대로 늘어납니다 |
| **DB 제약** | Oracle은 `IN` 절 1000개 제한이 있습니다. PostgreSQL은 하드 제한이 없지만 커질수록 느려집니다 |

반대로 너무 작으면 왕복 횟수가 늘어 원래 문제로 돌아갑니다. **50~200 구간이 대부분의 서비스에서 무난하다**는 게 관행의 근거입니다.

## 왜 자체 토큰이 필요한가 — 4가지

### 1. 카카오 토큰에는 우리 서비스의 권한 정보가 없습니다 ← 가장 결정적

자체 JWT에는 이게 들어갑니다 ([JwtProvider.java:38-39](src/main/java/com/whale/order/global/auth/jwt/JwtProvider.java#L38-L39)):
```java
.subject(String.valueOf(memberId))   // 우리 DB의 PK
.claim("role", role.name())          // CUSTOMER / OWNER / ADMIN
```

카카오 토큰이 알려주는 건 "이 사람은 카카오 회원 12345다"까지입니다. **"이 사람이 우리 매장의 점주인가"는 카카오가 알 수 없습니다.** 어드민 API(`/api/admin/**`)의 권한 검사는 이 `role` 클레임으로 하는데, 카카오 토큰으로는 불가능합니다.

`memberId`도 마찬가지입니다. 주문·결제·장바구니가 전부 우리 DB의 `member_id`로 엮여 있는데, 카카오 토큰에는 카카오 고유 ID만 있습니다. 매 요청마다 `providerId → memberId` 조회를 위해 **DB를 한 번씩 더 타야** 합니다.

### 2. 요청마다 카카오에 물어봐야 합니다

카카오 토큰은 **불투명(opaque) 토큰**입니다. 유효성을 우리가 검증할 수 없어서, 매 요청마다 카카오 API를 호출해야 합니다.

| | 자체 JWT | 카카오 토큰 |
|---|---|---|
| 검증 방법 | 서명 확인 (로컬, 마이크로초) | 카카오 API 호출 (네트워크 왕복) |
| 카카오 장애 시 | 정상 동작 | **전체 서비스 인증 불가** |
| 호출량 제한 | 없음 | 카카오 쿼터에 종속 |

수천 명 동시 주문을 목표로 한 프로젝트에서 **모든 API 요청이 외부 의존성을 타는 구조**는 성립하지 않습니다. 카카오가 흔들리면 결제도 주문 조회도 전부 멈춥니다.

### 3. 로그인 수단이 두 개인데 인가는 하나여야 합니다

이 프로젝트는 `AuthProvider`가 `LOCAL`과 `KAKAO` 두 가지입니다. 자체 회원가입 사용자는 카카오 토큰이 애초에 없습니다.

```
[LOCAL 로그인]  ─┐
                 ├─→ 자체 JWT ─→ JwtAuthenticationFilter ─→ 모든 API
[KAKAO 로그인]  ─┘
```

자체 토큰으로 통일했기 때문에 **인증 수단이 몇 개로 늘어나도 그 뒤의 인가 로직은 하나**입니다. 나중에 네이버·구글을 붙여도 `OAuth2SuccessHandler`만 추가하면 되고, 필터·컨트롤러·서비스는 손대지 않습니다.

### 4. 만료·무효화를 우리가 통제해야 합니다

카카오 토큰의 수명은 카카오가 정합니다. 우리 서비스의 정책(로그아웃 시 즉시 무효화, 강제 로그아웃, 리프레시 주기)을 적용할 수 없습니다.

자체 리프레시 토큰은 Redis에 `refresh:{memberId}`로 저장해서([RefreshTokenService](src/main/java/com/whale/order/global/auth/RefreshTokenService.java)) **키 하나 삭제로 즉시 무효화**할 수 있습니다.

## 답변 스크립트

> 카카오가 준 토큰은 **인증(Authentication)에만** 쓰고, 이후 요청은 자체 JWT로 처리합니다. 이유는 네 가지입니다.
>
> 첫째, **카카오 토큰에는 우리 서비스의 인가 정보가 없습니다.** 카카오는 "이 사람이 카카오 회원 12345다"까지만 알려주지, 이 사람이 점주인지 일반 고객인지는 모릅니다. 저희는 JWT에 우리 DB의 `memberId`와 `role`을 클레임으로 넣어서, 어드민 API 권한 검사를 토큰만으로 처리합니다.
>
> 둘째, **카카오 토큰은 불투명 토큰이라 매 요청마다 카카오 API를 호출해야 합니다.** 자체 JWT는 서명 검증만으로 끝나서 네트워크 왕복이 없고, 카카오에 장애가 나도 이미 로그인한 사용자는 정상 이용할 수 있습니다. 동시 주문 처리를 목표로 한 프로젝트에서 모든 요청이 외부 API에 의존하는 건 성립하지 않는다고 봤습니다.
>
> 셋째, **로그인 수단이 자체 회원가입과 카카오 두 가지**인데, 자체 가입 사용자는 카카오 토큰이 없습니다. 자체 토큰으로 통일해야 인증 수단이 늘어나도 그 뒤의 인가 로직을 하나로 유지할 수 있습니다.
>
> 넷째, **만료와 무효화를 우리가 통제**해야 합니다. 리프레시 토큰을 Redis에 저장해서 로그아웃 시 키를 지우면 즉시 무효화됩니다. 카카오 토큰은 수명을 카카오가 정하니 이런 정책을 걸 수 없습니다.
>
> 정리하면 **OAuth2는 "이 사람이 누구인지 확인하는 절차"까지만 담당하고, 그 이후 세션 관리는 서비스가 책임지는 게 표준적인 분리**라고 이해하고 있습니다.


`http_server_requests_seconds_bucket` 시리즈 자체가 존재하지 않으므로 **이 패널들은 "No data"로 뜹니다.** p50·p95·p99 세 패널 모두 해당합니다.

## 고치는 법 — yaml 몇 줄

```yaml
management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
        order.processing.time: true
      slo:
        http.server.requests: 50ms, 100ms, 200ms, 500ms, 1s, 2s
```

`percentiles-histogram: true`가 `_bucket` 시리즈를 만들어주고, 그때부터 대시보드의 `histogram_quantile()`이 동작합니다.

### `percentiles`와 헷갈리지 마세요 — 면접 단골입니다

| 설정 | 계산 위치 | 여러 인스턴스 집계 |
|---|---|---|
| `percentiles-histogram: true` | **Prometheus**가 버킷으로 계산 | **가능** ✅ |
| `percentiles: 0.95, 0.99` | **애플리케이션**이 계산해 값으로 전송 | **불가능** ❌ |

후자는 인스턴스별 p95가 각각 나오는데, **백분위수는 평균 낼 수 없어서** 여러 서버의 p95를 합칠 방법이 없습니다. 대시보드가 `histogram_quantile`을 쓰고 있으니 전자가 맞습니다.

## p95 = "얼마나 빨랐나", 성공률 = "얼마나 성공했나"

| | p95 | 성공률(`rate`) |
|---|---|---|
| 측정 대상 | **응답 시간** | **실패 건수 비율** |
| 읽는 법 | "요청의 95%가 2초 안에 끝났다" | "실패가 5% 미만이다" |
| 단위 | 밀리초 | 비율 |

`p(95)<2000`은 성공/실패와 **무관**합니다. 500 에러가 절반이어도 그것들이 빨리 떨어지면 p95는 통과합니다. 반대로 100% 성공해도 느리면 실패합니다. 그래서 k6에서 항상 짝으로 겁니다.

## 왜 평균이 아니라 p95인가

```
요청 100건: 95건은 100ms, 5건은 10초

평균 → 595ms   "괜찮네"
p95  → 10초    "20명 중 1명은 10초를 기다린다"
```

평균은 소수의 느린 요청을 희석시켜 **문제를 감춥니다.** p95는 "가장 느린 5%를 제외한 최악값"이라 실제 사용자 체감에 가깝습니다. 사이렌 오더처럼 피크에 몰리는 서비스는 평균이 아니라 꼬리(tail)가 문제라서 p95·p99를 봅니다.
