HMAC 대칭키라서 그렇습니다. [JwtProvider.java:30](src/main/java/com/whale/order/global/auth/jwt/JwtProvider.java#L30) 을 보면:

```java
this.secretKey = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
```

이 문자열은 **해석되지 않고 그냥 바이트 배열로 변환되어 HMAC-SHA256 함수에 키 재료로 들어갑니다.** 파싱도, 키 유도(PBKDF2 같은)도, 포맷 검증도 없습니다. RSA 개인키처럼 소수 쌍이라는 수학적 구조를 만족해야 하는 게 아니라, 알고리즘 입장에선 그냥 "32바이트 이상의 아무 값"이면 됩니다. 그래서 의미 있는 문자열일 이유가 전혀 없습니다.

오히려 **랜덤이어야 하는 쪽에 가깝습니다.** 이 키의 유일한 보안 요건은 "공격자가 못 맞히는 것"이고, 그건 엔트로피로만 결정되기 때문입니다. `whale-order-secret-key` 같은 걸 쓰면 위험한 이유는:

공격자가 로그인 한 번 해서 자기 JWT를 손에 넣으면, 그 토큰 자체가 **오프라인 검증기**가 됩니다. 서버에 요청을 보낼 필요 없이 후보 키를 넣고 서명이 맞는지 혼자 계속 대조할 수 있습니다. 로그인 시도 횟수 제한도, 로그도 안 남습니다. hashcat에 JWT 전용 모드(16500)가 있을 정도로 정형화된 공격이고, 사전 단어 조합은 초당 수억 건 단위로 털립니다. 키가 뚫리면 `role: ADMIN`, `sub: 아무_회원ID` 인 토큰을 스스로 발급할 수 있으니 전체 계정 탈취입니다.

랜덤 문자열은 이 오프라인 공격에 대해 "전수 탐색 말고는 방법이 없음" 상태를 만듭니다. 그게 유일한 방어선입니다.

**길이 조건**: jjwt는 HS256에 256비트(32바이트) 미만 키가 들어오면 `WeakKeyException` 을 던지며 起動 실패합니다. dev 기본값이 `whale-order-dev-secret-key-minimum-32-characters-long` ([application-dev.yaml:45](src/main/resources/application-dev.yaml#L45)) 로 길게 적혀 있는 게 그 이유입니다 — 보안이 아니라 길이 요건을 맞추려고 늘린 문자열이고, 값 자체는 공개 저장소에 있으니 dev 전용입니다.

운영 키 생성은 이걸로 충분합니다:
```bash
openssl rand -base64 48
```
base64는 문자당 6비트라 48바이트 → 64자 → 실질 엔트로피 384비트. 32자만 뽑으면 코드가 UTF-8 바이트를 그대로 키로 쓰기 때문에 길이 검사는 통과하지만 실엔트로피는 192비트로 떨어집니다. 여유 있게 뽑는 게 낫습니다.

한 가지 운영상 주의점: 이 값을 바꾸면 **기존에 발급된 모든 토큰이 즉시 무효화**됩니다. 리프레시 토큰이 Redis에 남아 있어도 서명 검증에서 떨어지니 전원 재로그인입니다. 그래서 `.env` 의 `JWT_SECRET` 은 한 번 정하면 고정해야 하고, [deploy.yml:53-54](.github/workflows/deploy.yml#L53-L54) 주석대로 `.env` 가 gitignore라 `git reset --hard` 에도 보존되는 구조입니다.

## 이 프로젝트에서 실제로 성립하는 근거

**1. 카카오 SSO 리다이렉트 플로우와 SPA를 잇는 수단**

[OAuth2SuccessHandler](src/main/java/com/whale/order/global/auth/oauth2/OAuth2SuccessHandler.java) 가 카카오 인증 완료 후 프론트(`/oauth2/callback`)로 리다이렉트하면서 토큰을 넘깁니다. 리다이렉트는 서버가 브라우저에 URL 하나만 던지는 단방향이라, 여기서 인증 결과를 전달하려면 **자기완결적인 문자열**이 필요합니다. 세션 방식이면 도메인/쿠키 설정에 묶이는데, 토큰은 그냥 URL에 실어 보내면 프론트가 받아 저장하면 끝입니다.

**2. SSE가 헤더 인증을 요구함**

이게 제일 구체적인 근거입니다. [event.js:20](frontend/src/api/event.js#L20) 주석 그대로 — `EventSource` 는 Authorization 헤더를 못 실어서 fetch + ReadableStream 으로 직접 구현했고, [event.js:30](frontend/src/api/event.js#L30) 에서 `Bearer` 토큰을 붙입니다. 실시간 주문 상태 스트림이 프로젝트 핵심 요구사항인데, 이 커넥션 인증을 헤더로 처리하는 구조 자체가 토큰 기반입니다.

**3. 세션을 완전히 버린 게 아니라, 필요한 곳만 남김**

[SecurityConfig.java:37-40](src/main/java/com/whale/order/global/config/SecurityConfig.java#L37-L40) 이 `IF_REQUIRED` 인 이유를 설명할 수 있으면 점수가 올라갑니다. OAuth2 인가 코드 플로우는 CSRF 방어용 `state` 파라미터를 서버가 기억해야 해서 세션이 불가피하고, 그 외 API 요청은 [JwtAuthenticationFilter](src/main/java/com/whale/order/global/auth/jwt/JwtAuthenticationFilter.java) 가 매번 토큰만 보고 처리합니다. "무조건 stateless"가 아니라 **프로토콜상 상태가 필요한 구간만 세션을 쓰고 나머지는 토큰**이라고 답하면, 유행 따라 붙인 게 아니라는 인상을 줍니다.

## 되받아칠 질문과 답

**"JWT는 로그아웃/강제만료가 안 되잖아요?"** — 가장 높은 확률로 나옵니다.

액세스 토큰은 30분으로 짧게 잡고([application.yaml:66](src/main/resources/application.yaml#L66)), 실질적인 세션 수명은 Redis에 저장한 리프레시 토큰이 통제합니다. [RefreshTokenService.delete()](src/main/java/com/whale/order/global/auth/RefreshTokenService.java#L38) 로 키를 지우면 재발급 경로가 끊겨서 최대 30분 내에 접근이 끝납니다. 즉 **"완전 무상태를 포기하고 리프레시만 서버 상태로 두는" 절충**을 의도적으로 택했다는 게 답입니다. 이건 실제 코드가 그렇게 되어 있으니 자신 있게 말해도 됩니다.

**"세션 써도 되지 않았나요?"**

솔직하게 "규모상 세션도 충분했다, 다만 SSO 리다이렉트 전달과 SSE 헤더 인증 두 지점에서 토큰이 더 자연스러웠다"고 하는 편이 낫습니다. 면접관은 기술 선택의 **트레이드오프를 아는지**를 보지, 무조건 JWT가 우월하다는 주장을 기대하지 않습니다.

## 실제로 벌어지는 일

```
[요청 1] 브라우저 → 우리서버  GET /oauth2/authorization/kakao
         서버: state="a8f3..." 랜덤 생성 → 세션에 저장 (JSESSIONID 쿠키 발급)
         서버: 카카오로 리다이렉트 (...&state=a8f3...)

         ─── 브라우저가 kauth.kakao.com 으로 떠남. 사용자가 카카오에서 로그인 ───

[요청 2] 카카오 → 브라우저 → 우리서버  GET /login/oauth2/code/kakao?code=XXX&state=a8f3...
         서버: 세션에 저장해둔 state 와 URL 로 돌아온 state 비교
              같으면 → code 로 토큰 교환 → KakaoOAuth2UserService → OAuth2SuccessHandler → JWT 발급
              다르면 → 거부
```

요청 1과 요청 2는 **완전히 별개의 HTTP 요청**입니다. 그 사이 우리 서버는 아무것도 안 하고 있었고, 요청 2는 카카오가 브라우저를 떠밀어서 온 겁니다. "이 콜백이 내가 시작시킨 그 로그인 맞나?"를 판단할 근거가 서버 메모리 말고는 없습니다. JWT는 여기서 못 씁니다 — **아직 로그인이 안 끝나서 발급할 토큰 자체가 없기 때문**입니다. JWT는 이 과정의 *결과물*이지 도구가 아닙니다.

## state 가 막는 공격

없으면 이런 게 됩니다. 공격자가 자기 카카오 계정으로 로그인을 진행해 `code`를 하나 얻어둡니다. 그리고 피해자에게 `우리서버/login/oauth2/code/kakao?code=공격자꺼` 링크를 클릭하게 만듭니다. 피해자 브라우저에서 그 코드가 처리되면, **피해자 세션에 공격자의 카카오 계정이 연결**됩니다. 이후 공격자가 자기 카카오로 로그인하면 피해자 계정에 들어갑니다. (로그인 CSRF)

state 가 있으면 이 링크는 그냥 죽습니다. 피해자 브라우저 세션엔 `a8f3...` 같은 값이 저장된 적이 없으니 비교 단계에서 걸립니다.

## 그래서 IF_REQUIRED

`SessionCreationPolicy` 세 가지 중:

| 값 | 동작 |
|---|---|
| `ALWAYS` | 모든 요청에 세션 생성 — 낭비 |
| `IF_REQUIRED` | 필요할 때만 생성 ← 현재 설정 |
| `STATELESS` | 세션을 **만들지도, 읽지도 않음** |

`STATELESS` 로 바꾸면 요청 1에서 state를 저장할 곳이 없어서, 요청 2에서 `authorization_request_not_found` 로 카카오 로그인이 통째로 깨집니다. 이게 [SecurityConfig.java:37-40](src/main/java/com/whale/order/global/config/SecurityConfig.java#L37-L40) 주석이 말하는 "세션이 필요"의 실체입니다.

반대로 `IF_REQUIRED` 여도 일반 API 요청에서는 세션이 안 생깁니다. [JwtAuthenticationFilter](src/main/java/com/whale/order/global/auth/jwt/JwtAuthenticationFilter.java) 가 헤더의 토큰만 읽고 `SecurityContext` 를 채우기 때문에 세션을 건드릴 일이 없거든요. **"필요하면 만든다"는 정책이지 "항상 만든다"가 아니라서, 실제로 세션이 생기는 건 카카오 로그인 핸드셰이크 몇 초 동안뿐**입니다. 그마저도 JWT가 발급되고 나면 더 이상 쓰이지 않습니다.

```
[진입]  EventQueueFacade.tryJoin()  → RRateLimiter 초당 100명 통과, 초과 시 429
[대기]  EventQueueService.join()    → ZSET에 timestamp 스코어로 등록
[처리]  EventScheduler.processQueues()  3초마다 재고만큼(≤10) 앞에서 꺼내 권한 부여 + SSE
```

## 1층: JPQL @Query — N+1 방어가 주목적

이벤트 도메인 포함해서 대부분 여기 해당합니다. 조건 자체는 단순하고, 실제 난이도는 **`open-in-view: false` 환경에서 LazyInitializationException 을 피하는 fetch join 설계**에 있습니다.

```java
// EventRepository.java:33
@Query("SELECT e FROM Event e JOIN FETCH e.goods ORDER BY e.openAt DESC")
```
[EventRepository.java:32](src/main/java/com/whale/order/domain/event/repository/EventRepository.java#L32) 주석이 그 이유를 그대로 적어두고 있습니다. 트랜잭션 밖(컨트롤러/직렬화 시점)에서 프록시를 건드리면 터지니, 필요한 연관을 쿼리 안에서 미리 끌어옵니다.

락도 이 층에서 처리합니다 — [EventRepository.java:20-22](src/main/java/com/whale/order/domain/event/repository/EventRepository.java#L20-L22) 의 `@Lock(PESSIMISTIC_WRITE)` 로 이벤트 재고 차감을 직렬화합니다. 반면 [StockRepository.java:13](src/main/java/com/whale/order/domain/stock/repository/StockRepository.java#L13) 은 Redisson 분산 락이 앞단에서 이미 직렬화하므로 DB 락을 일부러 안 겁니다. **같은 재고 차감인데 도메인마다 락 전략이 다른 이유**를 설명할 수 있으면 좋은 소재입니다.

## 2층: Querydsl — 내 주문 목록 커서 페이징

유일한 Querydsl 사용처가 [OrderRepositoryCustomImpl.java](src/main/java/com/whale/order/domain/order/repository/OrderRepositoryCustomImpl.java) 입니다. 여기 어려운 지점이 두 개 있습니다.

**(1) 커서 조건을 행 값 비교로 표현**

JPQL로는 `(A, B) < (?, ?)` 튜플 비교를 못 씁니다. 그래서 `Expressions.booleanTemplate` 으로 네이티브 SQL 조각을 주입했습니다:

```java
// OrderRepositoryCustomImpl.java:57
Expressions.booleanTemplate("({0}, {1}) < ({2}, {3})",
        order.createdAt, order.orderId, cursor.createdAt(), cursor.orderId());
```

`A < ? OR (A = ? AND B < ?)` 로 풀어쓰는 흔한 방식 대신 이걸 쓴 이유는 [주석 40-43줄](src/main/java/com/whale/order/domain/order/repository/OrderRepositoryCustomImpl.java#L40-L43)에 있습니다 — OR 형태는 옵티마이저가 복합 인덱스 range scan 으로 못 풀고 필터로 떨어뜨릴 수 있는데, 행 값 비교는 `(member_id, created_at, order_id)` 인덱스를 그대로 타서 페이지가 깊어져도 비용이 일정합니다. 대신 PostgreSQL/MySQL 종속이라는 트레이드오프가 있고, 이식 가능한 대체 코드까지 주석에 적어놨습니다.

**(2) 동적 where — null 반환 패턴**

첫 페이지엔 커서가 없습니다. [cursorCondition()](src/main/java/com/whale/order/domain/order/repository/OrderRepositoryCustomImpl.java#L54) 이 `null` 을 반환하면 Querydsl 이 where 절에서 알아서 빼줍니다. `if` 분기로 쿼리를 두 벌 만들 필요가 없다 — 이게 Querydsl 을 쓴 실질적 이유입니다.

**(3) fetch join 을 ToOne 으로만 제한**

가장 설명 가치가 높은 부분입니다. `store` 만 fetch join 하고 컬렉션인 `orderItems` 는 일부러 뺐습니다:

```
컬렉션까지 조인하면 → 결과 행이 자식 개수만큼 뻥튀기
                  → limit 이 "주문 N건"이 아니라 "조인 결과 N행"을 자름
                  → Hibernate 가 전체를 메모리로 올려 페이징 (HHH000104 경고, 대용량 시 OOM)
```

대신 `orderItems`·`menu` 는 지연 로딩으로 두고, [application.yaml:26](src/main/resources/application.yaml#L26) 의 `default_batch_fetch_size: 100` 이 이걸 IN 절 한 방으로 묶습니다. **"페이징 + 컬렉션"은 fetch join 으로 동시에 못 푸는 문제라, 페이징은 쿼리로 컬렉션은 배치 페치로 분리했다"** 가 답변 골자입니다.

## 놓치기 쉬운 핵심: 보안그룹은 stateful

여기서 대부분 헷갈립니다. **인바운드로 들어온 요청의 응답은 아웃바운드 규칙과 무관하게 자동으로 나갑니다.** 반대도 마찬가지고요.

```
브라우저 → :443 요청   ← 인바운드 규칙 검사 O
서버 → 브라우저 응답   ← 아웃바운드 규칙 검사 X (자동 허용)

서버 → 카카오 API 요청  ← 아웃바운드 규칙 검사 O
카카오 → 서버 응답      ← 인바운드 규칙 검사 X (자동 허용)
```

그래서 "HTTPS 응답이 나가야 하니 아웃바운드 443을 열어야 하나?" 는 불필요합니다. 아웃바운드는 **서버가 먼저 말을 거는 경우**에만 필요합니다.

참고로 VPC의 **네트워크 ACL은 stateless** 라서 응답 트래픽까지 명시적으로 열어야 합니다. 이 둘을 구분하는 게 포인트고, 보안그룹은 기본 아웃바운드 전체 허용이라 보통 인바운드만 만지게 됩니다.

## 실무에서는

AWS 보안그룹의 **아웃바운드 기본값이 `All traffic / 0.0.0.0/0` 전체 허용**입니다. 그래서 대부분 아웃바운드는 손대지 않고 인바운드만 관리합니다. 지금 이 프로젝트도 그 상태일 가능성이 높습니다.

굳이 아웃바운드를 조이는 건 규제 환경이나 침해 후 데이터 유출(exfiltration) 방지가 목적일 때입니다. 그때는 인바운드를 베끼는 게 아니라 **서버가 먼저 접속하는 대상**을 나열해야 합니다. 이 프로젝트라면:

- 443 → Docker Hub (`docker-compose pull`), 카카오 API(`kauth`/`kapi.kakao.com`), Let's Encrypt (Caddy 인증서 발급)
- 80 → apt 저장소, Let's Encrypt HTTP-01 검증
- 53 → DNS

보시면 인바운드 목록(80/443/22)과 겹치는 것도 있고 아닌 것도 있는데, **겹치는 건 우연**입니다. 인바운드 443은 "브라우저가 나에게", 아웃바운드 443은 "내가 카카오에게" — 완전히 다른 트래픽입니다.

반대로 **인바운드 22(SSH)에 대응하는 아웃바운드 22는 필요 없습니다.** 내 서버가 다른 서버로 SSH 접속할 일이 없으니까요. 미러링이 왜 무의미한지 보여주는 가장 명확한 예입니다.

## 코드에서 눈여겨볼 두 가지

**동시 401 처리** — [client.js:47-54](frontend/src/api/client.js#L47-L54). 화면에서 API 3개를 동시에 호출하다 셋 다 401을 받으면, `isRefreshing` 플래그 없이는 refresh가 3번 나갑니다. 그런데 서버가 RTR(Refresh Token Rotation)이라 첫 갱신 때 기존 토큰이 [Redis에서 교체](src/main/java/com/whale/order/global/auth/RefreshTokenService.java#L25)되므로, 2·3번째는 실패하고 로그아웃됩니다. 큐에 모아뒀다가 한 번만 갱신하고 결과를 나눠주는 게 그래서 필요합니다. 면접에서 "RTR 쓰면 동시 요청은 어떻게 하냐" 물어보면 여기를 짚으면 됩니다.

**무한 루프 방지** — [client.js:36](frontend/src/api/client.js#L36) 의 `original._retry` 체크. 재시도한 요청이 또 401이면 그냥 실패시킵니다. 이게 없으면 401 → refresh → 재시도 → 401 → … 이 됩니다.

## 그럼 Redis 사본은 왜 필요한가

③번 대조가 없다면 서명만 맞으면 통과입니다. 그러면:

- **로그아웃이 불가능**합니다. [logout()](src/main/java/com/whale/order/domain/member/service/MemberService.java#L197) 이 Redis 키를 지우는 걸로 세션을 끊는데, 대조를 안 하면 지워봐야 의미가 없습니다
- **탈취 감지가 불가능**합니다. [MemberService.java:187-191](src/main/java/com/whale/order/domain/member/service/MemberService.java#L187-L191) 이 그 처리입니다

두 번째가 RTR의 핵심 장치라 짚어둘 만합니다. 갱신할 때마다 [:193](src/main/java/com/whale/order/domain/member/service/MemberService.java#L193) 이 기존 토큰을 지우고 새로 발급하므로, 한 토큰은 **딱 한 번만** 쓸 수 있습니다.

```
공격자가 리프레시 토큰 탈취 → 먼저 사용 → 성공, Redis에는 공격자용 새 토큰이 저장됨
정상 사용자가 원래 토큰으로 갱신 시도 → stored 와 불일치
   → refreshTokenService.delete()  ← 공격자 토큰까지 통째로 폐기
   → 양쪽 모두 재로그인 필요
```

토큰이 재사용됐다는 건 사본이 둘 존재한다는 뜻이고, 누가 진짜인지 서버는 구분할 수 없으니 **둘 다 끊는 게 정답**입니다. 사용자는 한 번 다시 로그인하면 되지만 공격자는 비밀번호가 없어 못 들어옵니다.

## 정리하면

| | 클라이언트가 보내는 것 | Redis가 가진 것 |
|---|---|---|
| 역할 | 신원 제시 + 소유 증명 | 정답지 (대조용) |
| 없으면 | 누구인지 알 수 없음 | 로그아웃·탈취 감지 불가 |

"서버가 갖고 있으니 안 보내도 되지 않나"는 **비밀번호를 DB에 저장해두니 로그인할 때 안 쳐도 되지 않나**와 같은 구조입니다. 서버가 가진 건 대조용이지, 지금 요청한 사람이 그 주인이라는 증명은 아닙니다.
