`DELETE /api/members/me` 의 **요청 본문**입니다. 담는 값은 비밀번호 하나뿐입니다.

```java
public record WithdrawRequest(String password) {}
```

## 흐름

```
클라이언트  { "password": "pw1234!" }
    ↓
MemberController:74   @RequestBody(required = false) WithdrawRequest request
    ↓
MemberService:186     withdraw(memberId, request)
    ↓
MemberService:196     LOCAL 이면 passwordEncoder.matches() 로 검증
```

## 설계상 특이한 점 2가지

**1. `@NotBlank` 를 안 걸었습니다**

비밀번호 필수 여부가 **회원 종류에 따라 갈리기 때문**입니다.

| | 비밀번호 |
|---|---|
| LOCAL | 필수 (재확인용) |
| KAKAO | 없음 — `Member.password` 가 애초에 `null` |

Bean Validation은 "이 필드는 다른 필드 값에 따라 필수"를 표현하지 못합니다. 그래서 DTO는 값을 나르기만 하고, 판단은 [MemberService.java:195-201](src/main/java/com/whale/order/domain/member/service/MemberService.java#L195-L201) 에서 `provider` 를 보고 합니다.

**2. `request` 자체가 `null` 일 수 있습니다**

카카오 회원은 보낼 게 없어서 body를 통째로 생략할 수 있습니다. 그래서 [MemberController.java:74](src/main/java/com/whale/order/domain/member/controller/MemberController.java#L74) 가 `@RequestBody(required = false)` 이고, 서비스는 [MemberService.java:196](src/main/java/com/whale/order/domain/member/service/MemberService.java#L196) 에서 null을 먼저 걷어냅니다.

```java
String password = (request == null) ? null : request.password();
if (password == null || password.isBlank() || !passwordEncoder.matches(...)) {
    throw new IllegalArgumentException("비밀번호가 올바르지 않습니다");
}
```

`request` 가 null이든 `password` 가 null/공백이든 **LOCAL 회원에게는 전부 400**으로 수렴합니다. KAKAO 회원은 이 `if` 블록 자체를 타지 않습니다.

## 왜 `String password` 파라미터가 아니라 record인가

`@RequestBody` 로 JSON 본문을 받으려면 타입이 필요합니다. 필드 하나짜리 record가 과해 보일 수 있지만, 이 프로젝트의 다른 요청 DTO(`PasswordChangeRequest`, `MyProfileUpdateRequest`)와 같은 형태라 일관됩니다. 나중에 탈퇴 사유 같은 필드를 붙이기도 쉽고요.

## 왜 별도 테이블이 아닌가

**관계가 1:1입니다.** 재가입을 새 회원으로 처리하기로 했으니([Member.withdraw()](src/main/java/com/whale/order/domain/member/entity/Member.java) 가 `userId` 슬롯을 반납), 한 `member` row 는 **평생 한 번만** 탈퇴합니다. 1:1 관계를 테이블로 쪼개면 조회할 때마다 JOIN만 늘어납니다.

**익명화 정책이라 row 가 안 사라집니다.** 별도 테이블의 최대 강점은 "회원을 물리 삭제해도 통계가 남는다"인데, 우리는 `member` row 를 영구 보존합니다. 그 강점이 성립하지 않습니다.

**탈퇴 상태가 이미 `member` 에 있습니다.** `is_deleted` 옆에 사유가 붙는 게 자연스럽습니다. 테이블을 나누면 "탈퇴했는지는 A테이블, 왜 나갔는지는 B테이블"로 갈립니다.

## 진짜 중요한 결정: 자유 텍스트 vs enum

**enum(선택형)을 강하게 추천합니다.**

자유 입력이면 이런 게 들어옵니다.

```
"직원이 불친절해서요. 010-1234-5678로 연락주세요"
```

**`withdraw()` 가 개인정보를 지우는데, 그 옆 컬럼에 개인정보가 새로 쌓입니다.** 익명화를 하는 의미가 사라집니다.

```java
public enum WithdrawReason {
    NOT_USING,        // 자주 이용하지 않음
    INCONVENIENT,     // 사용이 불편함
    PRICE,            // 가격 부담
    SERVICE_QUALITY,  // 서비스 불만
    PRIVACY,          // 개인정보 우려
    OTHER             // 기타
}
```

## 구체적으로 붙일 것

컬럼 **2개**입니다.

| 컬럼 | 타입 | 이유 |
|---|---|---|
| `withdraw_reason` | `VARCHAR(30)` (enum) | 사유 |
| `withdrawn_at` | `LocalDateTime` | 탈퇴 시각 |

`withdrawn_at` 이 따로 필요합니다. [BaseEntity.java:37](src/main/java/com/whale/order/global/entity/BaseEntity.java#L37) 의 `updatedAt` 은 **아무 수정에나 갱신되므로** 탈퇴 시각으로 쓸 수 없습니다.

```java
public void withdraw(WithdrawReason reason) {
    // ... 기존 익명화 ...
    this.withdrawReason = reason;
    this.withdrawnAt = LocalDateTime.now();
    this.isDeleted = true;
}
```

`WithdrawRequest` 에 필드 하나 추가하면 API 변경도 끝납니다.

```java
public record WithdrawRequest(String password, WithdrawReason reason) {}
```

- **한 회원이 여러 번 탈퇴** — 재가입 시 기존 회원을 복구하는 정책으로 바꾸면 1:N이 됩니다
- **컬럼이 4~5개로 증가** — 상세 텍스트, 재가입 의향, 만족도 점수 등
- **탈퇴자 물리 삭제 정책 도입** — 그때는 통계를 분리 보관해야 합니다

지금은 컬럼 2개짜리 1:1이라 테이블을 나눌 이유가 없습니다.

## 진짜 원인은 두 개였습니다

### 1. 역직렬화 실패가 500으로 새고 있었다

`HttpMessageNotReadableException` 에 핸들러가 없어서, body를 못 읽으면 catch-all의 **"서버 오류가 발생했습니다"** 로 떨어졌습니다. 이게 보신 그 메시지입니다.

[GlobalExceptionHandler.java](src/main/java/com/whale/order/global/exception/GlobalExceptionHandler.java) 에 400 핸들러를 추가했습니다. 탈퇴뿐 아니라 **모든 API의 잘못된 body가 이제 원인을 알 수 있는 400**을 냅니다.

### 2. 앞서 "무관하다"고 한 테스트 실패 — 지금 것은 제 변경 탓입니다

정정합니다. 처음 봤을 때는 `Connection refused` 라 무관했지만, DB를 띄우신 뒤 드러난 실패는 **제가 만든 기능이 원인**입니다.

```
duplicate key value violates unique constraint "member_pkey"
Key (member_id)=(101) already exists.
```

연결 고리가 이렇습니다.

1. `testuser1`(member_id 101)로 **탈퇴를 테스트하셨습니다**
2. 익명화가 `user_id` 를 `deleted_101` 로 바꿔 **`testuser1` 슬롯을 반납**했습니다 (의도된 동작)
3. 다음 부팅 때 [LoadTestDataInitializer.java:37](src/main/java/com/whale/order/global/config/LoadTestDataInitializer.java#L37) 가 `user_id = 'testuser1'` 로 존재 여부를 보는데 없으니 시드를 재실행
4. [data-loadtest.sql:19](src/main/resources/data-loadtest.sql#L19) 의 `ON CONFLICT (user_id)` 도 같은 이유로 충돌을 못 잡음 → **member_id 101 PK 위반으로 부팅 실패**

**`user_id` 를 멱등성 기준으로 쓰던 게 문제였습니다.** 탈퇴가 생기면서 `user_id` 가 가변 값이 됐거든요. 둘 다 불변인 `member_id` 기준으로 바꿨습니다. (같은 파일의 메뉴·재고 INSERT는 원래 PK 기준이라 멀쩡했습니다.)

## 증거

**1. 백엔드는 정상** — 실제 서버에 직접 요청해본 결과, 프론트가 보낼 수 있는 모든 형태에서 올바른 메시지를 반환합니다.

```
{"password":"wrong"}                          → 400 {"message":"비밀번호가 맞지 않습니다"}
{"password":"wrong","reason":"NOT_USING"}     → 400 {"message":"비밀번호가 맞지 않습니다"}
Content-Type 없이                              → 400 {"message":"비밀번호가 맞지 않습니다"}
```

**2. Vite 개발 서버가 옛날 코드를 주고 있음** — `http://localhost:5173/src/pages/customer/MyProfilePage.jsx` 를 직접 받아보니:

```
탈퇴 모달 있음   : True
alert 있음      : False    ← 방금 추가한 alert이 없음
```

방금 넣은 `alert('탈퇴 처리되었습니다')` 가 서빙되는 코드에 **없습니다.** 파일에는 있는데 개발 서버가 못 읽고 있습니다. HMR이 변경을 놓친 상태입니다.

## 메시지 문구는 그대로 뒀습니다

`비밀번호가 맞지 않습니다` 로 바꾸지 **않았습니다.** 로그인 실패 문구는 두 분기가 일부러 똑같이 `아이디 또는 비밀번호가 올바르지 않습니다` 로 돼 있는데, 여기서 비밀번호 쪽만 다르게 말하면 **"이 아이디는 존재한다"** 를 알려주는 셈이라 계정을 긁어모을 수 있게 됩니다.

그래도 바꾸길 원하시면 말씀해주세요. 그 경우 아이디 미존재 분기도 같은 문구로 맞춰야 합니다.

(탈퇴 모달의 `비밀번호가 맞지 않습니다` 는 이미 로그인된 본인 확인이라 노출 위험이 없어서 그대로 두는 게 맞습니다.)
