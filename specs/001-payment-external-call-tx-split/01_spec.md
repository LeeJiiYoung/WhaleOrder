## 선행 작업 (001 구현 시작 시 첫 작업)

이 기능의 범위는 아니지만, 001 구현을 시작할 때 가장 먼저 처리한다.

- StockLockFacade의 InterruptedException 처리 수정
  - 현재: deductStock, restoreStock이 InterruptedException을 IllegalStateException으로 감싼다. KafkaConfig에서 IllegalStateException은 재시도 제외 대상이라 바로 DLT로 간다.
  - 문제: 배포 등으로 Kafka 컨슈머 스레드가 인터럽트되면 정상 주문이 DLT → 보상 트랜잭션 → 주문 취소·환불될 수 있다.
  - 수정: 재시도 대상인 StockLockException을 던지고 인터럽트 플래그(Thread.currentThread().interrupt())는 유지한다. offset이 커밋되지 않아 재시작 후 메시지가 다시 처리된다.
  - 테스트 먼저(Constitution VII-1): RLock.tryLock이 InterruptedException을 던질 때 StockLockException이 발생하고 인터럽트 플래그가 유지되는지 Mockito 단위 테스트로 검증한다.
  - 출처: docs/constitution-draft.md "초안 작성 중 발견한 불일치" 3번


## 배경

지금은 결제 승인과 결제 취소(환불)가 토스 API 호출을 DB 트랜잭션 안에서 한다. 그래서 세 가지 문제가 있다.

1. 토스 응답을 기다리는 동안 DB 커넥션과 행 락을 잡고 있다. 토스가 느려지면 커넥션 풀이 고갈될 수 있다.
2. 토스에서는 승인(또는 취소)이 끝났는데, 그 뒤 DB 커밋이 실패하면 기록이 사라진다.
   - 승인: 고객 돈은 나갔는데 주문은 결제 대기 상태로 남는다.
   - 취소: 환불은 됐는데 결제는 성공 상태로 남는다.
   지금은 이런 불일치를 알아챌 방법이 없다.
3. Redis 멱등 키가 사라진 상태에서 같은 승인 요청이 동시에 오면 토스 승인 API가 두 번 호출될 수 있다.


## 사용자 시나리오

### 시나리오 1. 정상 결제 승인
고객이 토스 결제창에서 결제를 마치면 주문이 접수 대기 상태가 되고, 고객 화면에 결제 완료가 표시된다. (현재와 동일)

### 시나리오 2. 같은 승인 요청이 동시에 두 번 들어옴
새로고침, 네트워크 재시도 등으로 같은 주문의 승인 요청이 동시에 와도 토스 승인은 한 번만 호출된다. 두 요청 모두 같은 결과를 받는다. Redis 멱등 키가 없어도 마찬가지다.

### 시나리오 3. 토스는 승인했는데 서버가 결과를 저장하지 못함
토스 승인 직후 서버가 죽거나 DB 저장이 실패해도, 결제는 "승인 진행 중"으로 남아 있다. 시스템은 일정 시간 뒤 토스에 실제 상태를 조회해 승인됐으면 성공으로, 아니면 실패로 정리한다. 고객 돈만 나가고 주문이 사라지는 일은 없다.

### 시나리오 4. 토스 승인 응답이 느리거나 타임아웃
고객 화면은 최대 10초만 기다린다. 10초가 지나면 주문 상세 화면으로 이동해 "결제 확인 중"을 보여주고, 주문 상세는 주기적으로 상태를 다시 조회해 결과가 나오면 바꿔 보여준다. 서버는 화면 이동과 관계없이 응답 타임아웃까지 기다려 결과를 저장한다. 타임아웃이 나면 시나리오 3과 같은 방식으로 실제 결과를 확인해 정리한다.


## 기능 요구사항

- FR-001: 결제 승인은 외부 PG 호출 중에 DB 트랜잭션을 열어두지 않아야 한다.
- FR-002: 결제에는 외부 승인 결과를 기다리는 "승인 진행 중" 상태가 있어야 한다.
- FR-003: 한 결제가 결제 대기에서 승인 진행 중으로 넘어가는 것은 동시에 여러 요청이 와도 하나만 성공해야 한다. 이 보장은 Redis 없이 DB만으로 성립해야 한다.
- FR-004: 진행 중 상태로 일정 시간 이상 멈춘 결제는 시스템이 외부 PG에 실제 상태를 조회해 정리해야 한다.
- FR-005: 정리 작업에서도 결과를 확정할 수 없으면(토스 조회 실패, 결제를 찾을 수 없음 등) 결제를 "확인 필요" 상태로 바꿔 DB에 남긴다. 확인 필요 상태의 결제는 정리 작업이 다시 조회하지 않는다. 확인 실패 사유는 결제 이력에 남긴다.
- FR-006: 모든 상태 변화는 기존처럼 결제 이력(PaymentHistory)에 남아야 한다.
- FR-007: 승인 성공 시 주문 이벤트 발행(Outbox)은 결제 성공 저장과 같은 트랜잭션에서 일어나야 한다. (Constitution III)
- FR-008: 고객이 보는 결제 결과는 성공, 실패, 확인 중 세 가지로 구분되어야 한다. 고객 화면은 승인 응답을 최대 10초만 기다리고, 넘으면 주문 상세에서 확인 중 상태를 보여준다.
- FR-009: 결제를 승인 진행 중으로 바꿀 때 외부 결제 식별자(paymentKey)를 함께 저장해야 한다. 정리 작업이 외부 PG에 조회할 수 있어야 하기 때문이다.
- FR-010: 외부 PG 호출에는 연결 타임아웃과 응답 타임아웃이 설정되어야 한다. 현재 TossPaymentClient는 타임아웃이 없어 무한 대기할 수 있다.
- FR-011: 응답 타임아웃이 나면 승인을 자동 재시도하지 않는다. 결제를 승인 진행 중으로 두고 FR-004의 정리 작업이 확정한다.
- FR-012: 주문 상세 화면은 결제가 확인 중이면 주기적으로 상태를 다시 조회해 결과를 반영해야 한다.
- FR-013: 관리자(ADMIN)는 별도 화면에서 확인 필요 상태의 결제 목록을 조회할 수 있어야 한다. 목록에는 주문 ID, 매장, 고객, 금액, paymentKey, 승인 시작 시각, 확정 실패 사유가 보인다.
- FR-014: 관리자는 목록에서 건별로 "토스 재조회"를 실행할 수 있어야 한다. 정리 작업과 같은 확인을 즉시 다시 하고, 확정되면 성공 또는 실패로 정리한다. 재조회 실행자와 시각은 결제 이력에 남긴다.
- FR-015: 결제가 승인 진행 중 또는 확인 필요 상태인 주문은 결제 대기 정리(PaymentSweepScheduler, cancelAwaitingPayment)가 취소하지 않아야 한다. 현재 이 정리 로직은 Redis 멱등 키로 confirm과의 충돌을 피하는데, 키 TTL(60초)이 지나면 보호가 사라져 토스에서 승인된 결제의 주문을 취소하고 결제를 실패로 바꿀 수 있다.
- FR-016: 승인 시작 시각부터 30분이 지난 뒤 토스 승인 완료로 확정된 결제는 주문을 접수하지 않는다. 결제는 SUCCESS로 기록한 뒤 주문을 CANCELLED(사유: 결제 확인 지연)로 바꾸고 환불을 요청한다. 환불까지 실패하면 결제를 확인 필요 상태로 두고 사유를 "환불 실패"로 남겨 관리자 화면에 계속 보이게 한다.


## 핵심 엔티티

- 결제(Payment): 상태에 "승인 진행 중", "확인 필요"가 추가된다. 진행 중 상태로 바뀐 시각을 알 수 있어야 한다.
- 결제 이력(PaymentHistory): 기존과 동일하게 모든 상태 전이를 기록한다.


## 성공 기준

- SC-001: 같은 주문으로 승인 요청을 동시에 20번 보내고 Redis 멱등 키를 무력화해도, 토스 승인 API 호출은 정확히 1번이다.
- SC-002: 토스 승인 호출 직후 DB 저장을 강제로 실패시켜도, 정리 작업이 돌고 나면 결제와 주문 상태가 토스의 실제 상태와 일치한다.
- SC-003: 토스 응답을 5초 지연시켜도 다른 주문의 결제 승인 처리가 그 지연에 영향을 받지 않는다.
- SC-004: 기존 결제·보상 관련 테스트(SagaCompensationTest, IdempotencyServiceTest 등)가 모두 통과한다.
- SC-005: 토스 응답을 30초 지연시켜도 고객 화면은 10초 안에 주문 상세의 "결제 확인 중"으로 넘어가고, 서버가 결과를 저장하면 주문 상세에 결과가 반영된다.
- SC-006: 토스 조회 API를 실패하도록 만들면 정리 작업 후 결제가 확인 필요 상태가 되고, 관리자 화면에 나타난다. 조회 API를 정상으로 되돌린 뒤 재조회하면 토스의 실제 상태로 정리된다.
- SC-007: 결제가 확인 필요 상태로 30분 이상 남아 있어도 결제 대기 정리 스케줄러가 해당 주문을 취소하지 않는다.
- SC-008: 승인 시작 후 30분이 지난 결제를 재조회해 토스 승인 완료가 나오면, 주문은 매장에 접수되지 않고 취소되며 환불이 요청된다.


## 범위 밖

- 확인 필요 결제의 수동 확정(관리자가 직접 성공/실패로 확정): 성공 확정 시 주문 접수와 Kafka 후속 흐름까지 이어져야 해 범위가 커진다. 별도 기능으로 한다. 그 전까지 Constitution IV-1 규칙 3의 "수동 해결" 경로는 토스 재조회만 제공된다.
- 점주(OWNER)용 확인 필요 결제 화면
- 결제 취소(환불)의 트랜잭션 분리: 이 기능에서 만든 패턴을 재사용해 다음 기능으로 진행한다. PaymentService.cancelPayment()는 이번에 바꾸지 않는다.
- 결제 준비(prepare)의 멱등성 강화: 중복 생성돼도 PaymentSweepScheduler가 정리한다.
- 보상 실패 자동 재처리: 별도 기능으로 진행한다. 이 기능은 기록과 알림까지만 책임진다.
- 실제 금액 결제: 토스 테스트 키 환경을 유지한다.


## Clarifications

### 2026-11-20

Q1. 범위: 승인과 환불을 한 번에 바꿀지, 승인 먼저 할지?
A. 승인(PaymentService.confirm)만 바꾼다. 환불(cancelPayment)은 다음 기능으로 한다. 환불 실패 시 동작 결정도 그때 한다.

Q5. 정리 작업에 토스 결제 조회 API를 쓸 수 있는가?
A. 쓸 수 있다고 본다. 조사 결과:
- 토스는 Idempotency-Key 헤더를 지원한다. 같은 키의 요청에는 같은 응답을 주며 키는 15일간 유효하다. (Toss Payments API 가이드)
- 특정 결제 조회는 paymentKey로 하는 것이 안전하다. orderId 조회는 결제위젯 키로는 안 되고 API 개별 연동 키가 필요하다는 토스 기술 지원 답변이 있다.
- 따라서 FR-009(승인 진행 중 전환 시 paymentKey 저장)를 추가했다.
- 현재 테스트 키 환경에서 paymentKey 조회가 실제로 되는지는 Plan 단계에서 직접 호출해 확인한다.


Q2. 정리 기준 시간과 외부 호출 타임아웃은?
A.
- 연결 타임아웃 5초: 연결 실패는 승인 요청이 토스에 도달하지 않았다는 뜻이므로 실패로 처리해도 안전하다.
- 응답 타임아웃 30초: 다른 PG사 권장 범위(30~60초) 안에서 고객 대기 시간을 줄이는 쪽을 택했다. 토스 공식 권장값은 찾지 못했다.
- 정리 기준 5분, 확인 주기 1분: 정상 요청은 길어야 약 35초(연결 5초 + 응답 30초) 안에 끝나므로 살아 있는 요청과 겹치지 않는다. 토스 승인 유효 시간(successUrl 이동 후 10분) 안이라, 조회 시 미승인이면 실패로 정리해도 결제는 토스에서 만료된다.
- 고객 최대 대기: 화면 응답 30초, 확인 중 상태 확정까지 최대 약 6분(기준 5분 + 주기 1분)
- 응답 도중 조회해 대기를 연장하는 방식은 검토 후 채택하지 않았다. 토스 승인은 동기 응답이라 중간 조회로 얻는 정보가 거의 없고 구현만 복잡해진다.

Q3. 확인 중일 때 고객 화면은?
A. 고객 대기 시간과 서버 타임아웃을 분리한다.
- 화면은 승인 응답을 최대 10초 기다린다. 응답이 오면 평소처럼 결과를 보여준다.
- 10초가 지나면 주문 상세로 이동해 "결제 확인 중"을 보여주고, 주문 상세는 주기적으로 상태를 조회한다.
- 서버는 30초 응답 타임아웃을 그대로 둔다. 클라이언트가 연결을 끊어도 서버 요청은 끝까지 실행되어 결과를 저장한다.
- 상태 갱신은 SSE가 아니라 주기적 조회로 한다. 현재 SSE는 단일 서버 메모리 기반이라 몇 분 단위 대기를 맡기기에 불안정하다.
- 검토한 대안: 승인 API 자체를 비동기(즉시 응답 후 백그라운드 승인)로 바꾸는 방식은 변경 범위가 커서 이번 기능에서 제외했다.
- 이 결정으로 프론트엔드(결제 결과 화면, 주문 상세 화면) 변경이 범위에 포함된다.

Q4. 정리 작업에서도 결과를 확정하지 못하면?
A. 결제를 "확인 필요" 상태로 바꿔 결제 자체에 기록한다. 이는 보상 실패(이미 성공한 것을 되돌리지 못함)가 아니라 결과 미확인이므로 보상 실패 테이블 결정(Constitution IV-1)과 분리한다.
- 관리자 화면: ADMIN 전용. 기존 재고 복구 실패 화면(StockRestoreFailurePage, /api/admin/stock-restore-failures)과 같은 방식으로 만든다.
- 기능: 목록 조회 + 건별 토스 재조회. 수동 확정은 범위 밖.
- OWNER 제외 이유: 결제 확인은 토스 대시보드를 봐야 하는 시스템 차원의 문제라 점주가 해결할 수 없다.

Q5-2. 재조회 결과에 따른 주문 상태는?
A.
- 확정 전(승인 진행 중, 확인 필요): 주문은 AWAITING_PAYMENT 유지. 매장 화면에 보이지 않고 고객 주문 상세에는 결제 확인 중으로 보인다.
- 토스 승인 완료: 결제 SUCCESS, 주문 PENDING, Outbox 이벤트 발행. 정상 결제와 같은 흐름이다.
- 토스 미승인: 결제 FAILED, 주문 CANCELLED. 토스 승인 거절과 같은 처리다.
- 확인 불가: 변화 없음. 확인 필요 상태 유지.
- 단, 승인 시작 후 30분이 지나 승인 완료로 확정되면 접수하지 않고 취소·환불한다(FR-016). 사이렌 오더 특성상 30분 넘게 늦은 주문은 고객이 이미 떠났을 가능성이 크다. 30분은 기존 결제 대기 정리 스케줄러 기준과 같다.
- 환불은 기존 PaymentService.cancelPayment()를 재사용한다. 이 메서드는 트랜잭션 안에서 토스를 호출하므로 Constitution 원칙 X의 임시 예외로 둔다. 다음 기능(환불 트랜잭션 분리)에서 해소한다.
- 검토한 대안: 주문만 취소하고 관리자가 토스 대시보드에서 직접 환불하는 방식은, 환불 완료를 시스템에 반영할 수동 확정 기능이 없어 기록이 어긋나므로 채택하지 않았다.
